# AI Design Skills and Agent Tooling

Initial audit: 2026-10-07; later reviews are dated by section (not a whole-file recertification).

## Purpose

Evaluate design skills as executable design infrastructure, not prompt collections or popularity contests. Keep this file selective: promotion requires source inspection and clear marginal value.

## Evaluation model

Before recommending an install, inspect the canonical repository for:

1. **Decision value** — judgment versus style presets.
2. **Workflow leverage** — grounding, exploration, implementation, rendered review, iteration.
3. **Evidence/provenance** — standards, platform guidance, practitioner heuristics, or observable implementation.
4. **Progressive disclosure** — load only relevant guidance.
5. **Verification** — inspect rendered states rather than infer quality from source/build success.
6. **Compatibility** — explicit support for the target harness; syntactic portability is not behavioral equivalence.
7. **Operational cost** — dependencies, hooks, browsers, generated files, context and update burden.
8. **Security/supply chain** — inspect installers, scripts, hooks and package execution separately from Markdown instructions.
9. **Maintenance/freshness** — canonical upstream, license, `archived`, `pushed_at`, commits/releases.
10. **Marginal value** — prefer complementary capabilities over overlapping anti-slop packs.
11. **Behavioral evidence** — distinguish installation/trigger success, output quality, and causal uplift. A skill that reliably activates is not thereby proven to improve the result.

Stars are adoption signal, never evidence of design quality or user outcomes.

## Recommended candidates


**Adversarial revalidation — manifest trust (2026-10-23):** A manifest is **derived documentation, not a complete source-of-truth for legal props**. Official Storybook guidance prefers `react-docgen-typescript` for rich prop extraction, but explicitly offers faster, less detailed `react-docgen` when generation is slow. In an open React docgen issue (#34710), an example component's manifest contained an `error` instead of props; a separate named-union-alias defect (#35778) was **closed as completed on 2026-10-15** (PR #36661), so do **not** repeat the older claim that it remains unfixed. Check the **installed version**, generated output and actual source before inferring any component lacks a prop. A 2026 OOM/timeouts report (#214) involved a large monorepo and remains a case report, not a blanket performance verdict.

**Operational fallback when agent grounding fails:** First check `docs-list`/`docs-show`, then the manifest debugger at `/manifests/components.html` for warnings and omitted components. With `experimentalDocgenServer`, **development** `/manifests/components.json` and `docs.json` can intentionally return 404; use the debugger or a **built** Storybook instead of diagnosing this as a broken server. If docgen reports errors or an alias is opaque, inspect the exported TypeScript prop types, JSDoc and representative stories; confirm the proposed usage with typecheck, rendered states and story tests. Treat the docs toolset as unavailable for unsupported frameworks, not as a reason to invent an API. Explicitly record any unresolved prop ambiguity.

**Permission and automation boundary:** Official 10.6 addon API exposes `dev`, `docs` and `test` toolset switches (all default true); `test-run` needs the Vitest addon, and an a11y gate needs explicit a11y configuration. Story `play` functions can interact with application state: mock real network/write side effects and use disposable fixtures before letting agents run tests. The inspected `next` addon preset checks browser Origin/JSON media type but **allows requests without an Origin header**, and only demands a bearer token when composition authentication requires it; these are **not** blanket authorization for a public dev MCP. Bind to trusted interfaces and use separate authentication for published/private docs. The experimental **Codex plugin** README states that setup/upgrade may insert or update a marked Storybook-skills block in `AGENTS.md` (and possibly Claude instruction files). Review those instruction-file diffs before accepting an autonomous plugin upgrade; project authority should not silently change.

**Promotion test:** On a pinned 10.6 project, seed a missing-docgen component, an aliased union prop, a large component inventory, a side-effecting story and a clean control. Compare source-only agent vs MCP-grounded agent on prop correctness, error/abstention behavior, startup/tool latency, actual story coverage, mutation safety, token cost and visual/accessibility outcomes. Only promote broad claims if the MCP version is pinned and both positive and negative controls behave as expected. **No benchmark or runtime reproduction was performed in this revalidation.**

### `pbakaus/impeccable` — direction, critique and refinement

**Status:** recommended candidate; active upstream and strong adoption signal as of 2026-10-05.

Provides a shared design vocabulary plus focused operations for auditing, polishing, simplifying, hierarchy, typography, color, responsiveness and motion, with deterministic detectors/hooks for recurring generated-UI problems.

**Best fit:** iterative visual refinement of existing or newly built interfaces. It changes the critique loop rather than merely asking an agent to “make it beautiful.”

**Boundary:** its anti-slop rules are opinionated heuristics, not universal prohibitions. Legitimate brand choices can intentionally violate them. Provider hooks increase trust surface and should be inspected.

**License:** Apache-2.0.

### `nextlevelbuilder/ui-ux-pro-max-skill` — retrieval and stack guidance

**Status:** recommended candidate, especially as a knowledge/retrieval layer.

Uses searchable local data for styles, product reasoning, palettes, typography, UX, icons, charts, motion and stack-specific implementation. Current upstream supports Claude Code, Codex and other agent environments. v2.15.0 reports relevance evaluation, provenance/freshness metadata, framework routing, abstention, semantic validators and automated tests; these retrieval-quality mechanisms matter more than catalog size.

**Best fit:** early grounding, design-system exploration, broad UX checks and stack questions.

**Boundary:** retrieved palettes/category rules are candidates, not evidence of preference. Broad catalogs can create false authority and category stereotypes. Fast-changing stack advice needs freshness checks; CLI/generated assets expand maintenance and supply-chain surface.

**License:** MIT.

### `emilkowalski/skills` — specialist motion and design engineering

**Status:** recommended specialist complement, not a general UX replacement.

Focused skills cover animation creation/review, interaction craft, design engineering, prototyping, mobile-native web details and adversarial UI breaking.

**Best fit:** motion, micro-interactions, direct manipulation and post-build craft. Narrow loading gives useful progressive disclosure.

**Boundary:** duration/easing/spring rules are practitioner heuristics; accessibility, product motion language, platform conventions and brand requirements can override defaults.

**License:** MIT.

### `daymade/claude-code-skills/frontend-visual-qa` — rendered verification

**Status:** recommended candidate for Claude Code when post-implementation verification is the missing capability.

Its strongest idea is falsifiable evidence: build success, DOM presence and uninspected screenshots are supporting signals, not visual proof. It defines target identity, state, viewport, journeys, reference/pass condition and then inspects the actual rendered artifact. It distinguishes visible browser/native evidence, browser/E2E geometry and interaction evidence, headless mechanical sweeps, and source/build reasoning.

**Best fit:** responsive defects, overflow/wrapping, conditional states, charts, browser output, reference parity and release-oriented visual review after a design/refinement skill has acted.

**Boundary:** currently Claude-oriented; do not infer Codex parity from Markdown readability. Browser/native tooling increases operational and trust surface. Visual QA cannot certify unexercised functional correctness, domain facts or user preference.

**License/maintenance:** parent repo MIT, unarchived and pushed 2026-10-05 when inspected.


### Vercel React Best Practices — useful performance rules, unsafe unqualified examples (reviewed 2026-10-24)

**Decision: conditional, high-value *implementation* skill for React/Next.js agents; not a UI-design skill, automatic performance certification, or permission to apply all 70 recipes.** The canonical Vercel-maintained `vercel-react-best-practices` skill has 70 individually addressable rules in eight priority groups, with incorrect/correct code samples and a large compiled `AGENTS.md`. Its strongest marginal value is targeted detection of independent data-fetch waterfalls, avoidable bundle work, unnecessary rendering and unsafe server-action authorization. It complements Impeccable's visual critique, Storybook's component contracts and browser QA rather than replacing them. The canonical README still says “40+” rules while `SKILL.md` enumerates 70: trust the reviewed files, not registry counts.

**Use it selectively:** inspect the actual framework/runtime (React Compiler enabled? Next App Router version? caching configuration? serverless instance sharing?), choose the relevant rule files, and ask the agent to justify a measured bottleneck and preserve correctness. Do **not** inject the ~106 KB compiled `AGENTS.md` into every task. No published installation or star count proves faster pages, fewer defects, or better UX.

| Inspected upstream rule | Where it helps | Failure mode / mandatory qualification |
|---|---|---|
| `async-parallel`, `async-dependencies` | Parallelize *independent* I/O; avoid avoidable waterfalls. | “2–10×” is an illustrative impact label, **not a measured general uplift**. Verify dependencies, concurrency budgets, failure/cancellation behavior and side effects; `better-all` is an **optional additional package**, not necessary for basic promise chaining. |
| `server-cache-react`, `server-cache-lru` | Deduplicate repeated server work within a request; optionally reuse genuinely shareable results across requests. | React `cache()` is request-scoped and caches errors; Next identical render-tree `fetch` memoization is **not** persistent data caching. The skill's cross-request LRU example `getUser(id)` has **no authorization/tenant partition in the sample**: copying it into a multitenant app can expose stale or unauthorized data if callers lack a per-request access check. TTL alone does not revoke access. Prefer request-scoped authorized DAL access for private data; cross-request caches only for explicitly safe data with scoped keys, invalidation and reauthorization. Fluid Compute may serve concurrent requests in one process. |
| `js-cache-function-results` | Cache deterministic, pure, expensive work with bounded reuse. | Its module-level `Map` has no eviction and its example caches `document.cookie.includes('auth=')` until an explicit callback. That value can become stale across session/tab changes; **never use client-cached login state as authorization**. Prefer bounded caches for public pure values and server-side permission checks. |
| `rendering-hydration-no-flicker`, `rendering-hydration-suppress-warning` | Identify theme/SSR mismatch hazards. | The suggested `<script dangerouslySetInnerHTML>` **after** a theme wrapper mutates its class before hydration, but does **not** prove it ran before first paint, that React's expected attributes still match, or that a strict CSP allows it. React warns that attribute mismatches may not be patched. `suppressHydrationWarning` is a one-level escape hatch, **not a repair**. Prefer a framework-compatible, CSP-approved theme initialization with matching initial DOM and a browser test; never infer authentication from localStorage. |
| `rendering-content-visibility` | Candidate render-skipping optimization for long independent sections. | The sample asserts ~990/1000 items skipped and “10× faster initial render” without a trace; this is **not a measured result**. Its fixed `contain-intrinsic-size: 0 80px` estimate can cause scroll displacement; no DOM nodes are removed and AT-tree behavior has spec exceptions. Follow this repository's offscreen-rendering contract instead of copying the claim. |
| `rerender-memo`, `server-auth-actions` | Conditional component optimization; strong reminder to authorize every server mutation. | The memo rule itself acknowledges React Compiler may remove the need for manual `memo/useMemo`. Confirm compiler coverage before adding churn. Keep the server-action authentication/authorization rule even when performance guidance is inapplicable. |

**Install/compatibility/maintenance:** canonical source: `vercel-labs/agent-skills/skills/react-best-practices` (`SKILL.md` frontmatter name `vercel-react-best-practices`, version `1.0.0` at review). Official skills CLI supports project-scoped `npx skills add vercel-labs/agent-skills --skill vercel-react-best-practices`; verify discovery and pin the reviewed revision before rollout. Agent Skills-capable Claude Code, Codex and compatible coding agents can consume the Markdown, but installation does not guarantee trigger or rule compliance. Inspected rule files are instructions, not a standalone executable optimizer; copying examples can introduce dependencies (`lru-cache`, `better-all`) or new state/security risk. The skill and README declare **MIT**, but a root `LICENSE` file was not found in the inspected repository path; confirm licensing requirements before redistribution. The installer (`npx`), upstream updates and any agent execution permissions remain separate supply-chain surfaces. The canonical source is maintained by Vercel; third-party mirrors may retain older rule counts or guidance.

**Agent falsification gate:** compare baseline agent versus skill on identical React/Next tasks and clean controls: independent/dependent fetches; two tenants requesting the same user ID with a revoked permission; logout in another tab; theme SSR under strict CSP and slow JS; 1,000 variable-height messages; React Compiler enabled/disabled; server-action authorization. Record verified network waterfalls, bundle size, render/INP/CLS traces, hydration warnings, correctness/security failures, rule-selection accuracy, token/context cost and unintended churn. A successful build, rule citation or prettier diff is not evidence of performance or UX improvement. **No local install, runtime exploit, benchmark or cross-agent trial was performed this cycle.**

### Official Playwright CLI skill — efficient browser exploration with an untrusted page-tool boundary (reviewed 2026-10-24)

**Decision: conditional recommendation for coding agents doing exploratory browser QA; not a design-quality oracle, WCAG audit, production-safe autonomous operator, or replacement for deterministic Playwright Test.** Microsoft's maintained Apache-2.0 Playwright project now ships `@playwright/cli` plus a first-party installable `playwright-cli` skill. It adds a shell-driven browser, scoped accessibility-tree snapshots/element refs, screenshot/trace/console/network inspection, emulation, test-generation guidance, and optional page-exposed WebMCP calls. The distinctive benefit is *less agent-context/tool-schema overhead*, not demonstrated higher defect-detection accuracy. GitHub Agentic Workflows switched its built-in Playwright integration to CLI-only on **2026-09-01** for operational/schema reasons, while retaining optional explicit MCP; this is a deployment choice, not a universal performance benchmark.

**Choose by task:** CLI + skill for coding agents with shell access, local development servers and selective browser inspection; MCP when structured tool permissions and iterative introspection fit the agent runtime; Playwright Test for reproducible CI assertions, fixture isolation and regression gates. The already documented `agent-browser` dogfood skill emphasizes broad exploratory review; neither tool automatically supplies visual judgment, AT testing or a conformance verdict. CLI snapshots describe *accessible structure*, not necessarily what is visible in the viewport or what users can operate at that moment. Element refs expire after page changes; resnapshot rather than retrying stale refs. Generated actions are not test assertions: write independent outcome, accessibility and failure-path assertions, then execute the tests. Compare against a clean control to avoid inventing bugs.

**Install / compatibility:** review/pin the package and copied skill before use. Official documentation requires Node.js 20+ and shows `npm install -D @playwright/cli@<reviewed-version>` followed by `npx playwright cli --help`, or a reviewed global install; `playwright-cli install --skills` copies into `.claude/skills/`, and `--skills=agents` into `.agents/skills/` (suitable for agents that load that convention). Documented agent support includes Claude Code, Copilot, Cursor and compatible skill-loading coding agents; verify Codex discovery in the actual environment rather than assuming a package label proves it. Browser binaries, Node/npm, shell permissions and local filesystem artifacts are dependencies. Avoid unreviewed `@latest`, global profile reuse, privileged browser attachments and installing dependencies on a production host. Official skill's `allowed-tools` grants broad `Bash(playwright-cli:*)`; constrain the *agent's* allowed actions separately.

**Important source-level counterexample — page tools are not agent instructions.** The inspected current `microsoft/playwright` skill explicitly says to prefer a page's experimental WebMCP tools over UI navigation, even noting they can bypass a cookie banner. But tool names, schemas, annotations, results and implementation come from **the visited page**, not Microsoft, and may act within an authenticated browser session. Chrome's first-party WebMCP security guidance identifies malicious tool metadata/output prompt injection, cross-origin exfiltration and consequential actions. Treat `webmcp-list` as discovery of *untrusted capabilities*, never an automatic authorization to call `webmcp-call`; do not let a tool shortcut bypass a required user choice/consent or product permission. Check origin/frame, task alignment, side effects, data scope and real authorization; do not rely solely on page-declared `readOnlyHint`/`consequentialHint`. Default to ordinary UI/verified APIs for unknown sites; use WebMCP only on reviewed test fixtures or approved origins, with independent outcome and audit checks. WebMCP remains experimental and its API/security model may change.

**Privacy and freshness traps:** snapshots, traces, screenshots, network records, `state-save` and browser profiles may expose credentials, cookies, personal data and test fixtures. A reported password-in-snapshot leak (`microsoft/playwright-cli#317`) was closed after maintainers pointed to a *secrets-file redaction mechanism*, not proof that every password field is automatically masked; validate redaction on the installed version and use synthetic credentials. The `microsoft/playwright-cli` repository's copied skill/reference files were still stale when inspected: they recommended nonexistent `toBeUnchecked()`, tracing before `open`, and incorrectly described `--raw` snapshot stripping. All three reports (#482/#480/#481) were **fixed in `microsoft/playwright` main on 2026-10-19**; do not present them as unresolved upstream bugs or assume the mirror/package already contains fixes. A separate CDP-attach report (#483, 2026-10-17) involves suspended-extension tabs; prefer isolated CLI-launched browsers over an arbitrary personal Chrome profile. Verify the *installed package/skill version*, not just main-branch documentation.

**Agent acceptance gate:** on an isolated app, compare (A) Playwright Test + source inspection, (B) CLI without skill, (C) CLI + reviewed skill, and (D) MCP on identical seeded visual, navigation, keyboard, form and async defects **plus clean controls**. Include stale refs, icon-only controls, a deceptive read-only WebMCP tool, a consent overlay, authenticated state, secret-bearing input, a CDP-attach edge case and a deliberately stale generated assertion. Measure confirmed defects, false claims, unintended state mutations, secret leakage, execution cost/tokens, time to *verified fix* and reproducibility; inspect artifacts and delete them securely. No local install, live browser experiment, adoption-rate analysis or cross-model comparison was performed in this review.

**Primary evidence (2026-10-24):** [Playwright CLI official guide](https://playwright.dev/docs/getting-started-cli), [skill installation](https://playwright.dev/agent-cli/skills), [snapshot/ref lifetime](https://playwright.dev/agent-cli/snapshots), [current first-party SKILL.md](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/tools/skills/playwright-cli/SKILL.md), [CLI vs MCP](https://playwright.dev/mcp/introduction), [GitHub's CLI-only decision (2026-09-01)](https://github.github.com/gh-aw/blog/2026-09-01-why-playwright-cli-replaces-playwright-mcp/), [fixed reference bugs #480/#481/#482](https://github.com/microsoft/playwright-cli/issues/480), [password snapshot report #317](https://github.com/microsoft/playwright-cli/issues/317), [CDP report #483](https://github.com/microsoft/playwright-cli/issues/483), [Chrome WebMCP agent security](https://developer.chrome.com/docs/agents/security), [Chrome WebMCP tool security](https://developer.chrome.com/docs/ai/webmcp/secure-tools).

### Official shadcn/ui skill and registry MCP — project-grounded composition, not design judgment (reviewed 2026-10-23)

**Status: conditional recommendation for existing shadcn/ui projects; install the skill first, add MCP only when live registry discovery is useful.** This is a *component implementation/grounding* capability, not a replacement for Impeccable's critique, Figma's design-source handoff, Storybook's project-specific stories/contracts, or browser-based verification. Inspected the official [skill source](https://github.com/shadcn-ui/ui/blob/main/skills/shadcn/SKILL.md), [forms](https://github.com/shadcn-ui/ui/blob/main/skills/shadcn/rules/forms.md), [styling rules](https://github.com/shadcn-ui/ui/blob/main/skills/shadcn/rules/styling.md), [MCP tool handlers](https://github.com/shadcn-ui/ui/blob/main/packages/shadcn/src/mcp/index.ts), [MCP helpers](https://github.com/shadcn-ui/ui/blob/main/packages/shadcn/src/mcp/utils.ts), and [CLI package](https://github.com/shadcn-ui/ui/blob/main/packages/shadcn/package.json) on 2026-10-23 (repo package v4.22.1, MIT, Node >=20.18.1; actively maintained official monorepo). These are **source-level findings**, not a tested uplift claim.

**Distinct mechanisms and fit.**
- **Skill:** project-scoped `SKILL.md` plus composition, forms, base-vs-Radix, styling, chat, design-system and CLI references. Its embedded `shadcn info --json` command reads actual `components.json`-derived framework, paths, icon library, Tailwind version and primitive base; this can prevent guessed imports and wrong Base/Radix APIs. It teaches `docs`, `search`, `view`, `--dry-run`, `--diff` and local-change-aware updates. Use when the project actually uses shadcn; do not add shadcn to a different stack merely to use this skill.
- **MCP:** the inspected server exposes **seven** tools: get registries, list/search/view items, get examples, get add command, and a minimal audit checklist. Crucially, `get_add_command_for_items` **returns a CLI command string; it does not itself install anything**. The connected agent can separately execute that command if shell access is granted. The audit checklist checks imports/dependencies/lint/types and suggests Playwright; it is **not an accessibility audit**. The skill already supports direct CLI/docs discovery, so MCP's marginal value is multi-registry browsing in clients where MCP is easier than shell.
- **Compatibility/install:** official [skill docs](https://ui.shadcn.com/docs/skills) show `pnpm dlx skills add shadcn/ui`; official [MCP docs](https://ui.shadcn.com/docs/registry/mcp) show `pnpm dlx shadcn@latest mcp init --client claude` and configurations for Cursor, VS Code, Codex and OpenCode. For Codex, docs show an `npx`-based `mcp_servers.shadcn` entry in `~/.codex/config.toml`. Verify the installed skill's path, client permissions and actual commands; an MCP-capable client does not automatically honor a skill's Bash permissions. No separate cloud API is needed for public registries; private registries can require credentials and network access.

**Two source-level cautions that can mislead agents.**
1. The skill declares `Option sets (2–7 choices) use ToggleGroup` as an **always-enforced** rule, while its own forms guide says `Single choice from few options → RadioGroup`. Both components exist, but they are not interchangeable by option count: an exclusive *form answer* generally calls for radio-group semantics (`aria-checked`, group label, radio keyboard behavior), whereas an on/off formatting/tool selection may call for pressed-toggle semantics (`aria-pressed`). A single-selection ToggleGroup is technically supported; the defect is the universal numerical rule, not the component. Choose by user task, semantics, submission and assistive-technology behavior; compare [W3C radio group](https://www.w3.org/WAI/ARIA/apg/patterns/radio/), [toggle button](https://www.w3.org/WAI/ARIA/apg/patterns/button/), [shadcn RadioGroup](https://ui.shadcn.com/docs/components/base/radio-group), and [ToggleGroup](https://ui.shadcn.com/docs/components/base/toggle-group).
2. Its categorical `className for layout, not styling`, `always use Card/Empty/Skeleton/Alert`, and default `Settings page = Tabs + Card` advice can help consistency but **must not override a product's information architecture, bespoke design contract or semantic HTML**. Repeated library-default compositions may also reinforce generic AI UI. Interpret these as conventions for the *selected* system, not universal design laws. Inspect real rendered work, rather than declaring compliance because the components match the skill.

**Security, freshness and maintenance gate.** The skill's `allowed-tools` grants broad `shadcn@latest *` shell commands; the MCP itself is registry-reading/command-producing, but an agent executing the returned `add`, `apply` or `init` command can change source, styles, config, dependencies and lockfiles. Universal/GitHub registries can ship **agent instructions and CI workflows**, not just React components; item `target`, `envVars`, `registryDependencies` and transitive package dependencies expand the trust boundary. Inspect upstream and the exact resolved payload; pin a known CLI version and GitHub registry **commit SHA** where reproducibility matters; preview with `view`/`add --dry-run`/`--diff`; review diffs and dependency install scripts; do not auto-execute instructions embedded in registry content. The official [GitHub registry security notes](https://ui.shadcn.com/docs/registry/github) recommend reviewing these fields and pinning refs. The experimental [Registry Health](https://ui.shadcn.com/docs/registry/health) score checks availability/schema/sample installability, **not security, accessibility, design quality or adoption**; it excludes private and direct GitHub registries. `@latest` can drift between sessions; inspect skill updates before reinstalling. See also [npm install-script behavior](https://docs.npmjs.com/cli/v11/commands/npm-install/).

**Decision workflow:** (1) confirm existing project uses shadcn and inspect local components/overrides; (2) read project config with a reviewed/pinned CLI; (3) search existing components before external registries; (4) inspect docs, resolved item contents, transitive files/dependencies and license; (5) use a separate reviewed install/change step; (6) preserve local modifications and run typecheck/build plus keyboard, screen-reader, zoom, responsive, light/dark and real browser tests. Do **not** use the skill to certify accessibility, decide whether a page needs tabs/cards, or replace design critique.

**Alternatives and falsification:** direct CLI + project source inspection may be sufficient with lower agent/tool overhead; Storybook MCP is better for a team's **actual stories/props**, Figma Code Connect for **mapped design components**, and Playwright/axe/manual AT for **behavior**. Compare direct CLI/docs, skill-only and skill+MCP on matched tasks with different primitive bases, nonstandard aliases, intentionally stale component APIs, a three-option *form* radio question, custom design requirements, and a malicious-looking registry item. Measure incorrect imports/props, semantic regressions, unauthorized file changes, time/token cost, and rendered fidelity. **No controlled trials or measured design-quality uplift established; do not raise agent-workflow maturity.**

### Storybook MCP and official agent plugins — live component contracts (revalidated 2026-10-23)

**Status: conditional recommendation for teams already using Storybook; preview/experimental, not a general-purpose design skill.** This is a different capability from Impeccable (critique), Figma MCP (design-source handoff), or screenshot QA (real-page verification): an agent queries the project's **actual documented components, props and stories**, writes representative states, then runs component/axe checks. Its value depends on documentation coverage and story quality; it cannot invent a trustworthy design system from a weak one.

**Source and freshness:** use the maintained `storybookjs/storybook` monorepo (`code/addons/mcp`, `code/lib/codex-plugin`, `code/lib/claude-plugin`). The former `storybookjs/mcp` repo was **archived 2026-09-07** and its install instructions are historical. Official MCP addon docs describe the 10.3+ path; the new Claude/Codex **plugins require Storybook 11 prerelease or later** and remain experimental (inspected `next` source packages are 11.0.0-alpha.8). Do not mix these installation paths or assume 11-alpha plugin behavior is stable.

**Mechanism / fit:** `@storybook/addon-mcp` serves a local `/mcp` endpoint with docs (`docs-list`, `docs-show`, `docs-show-story`), development (story instructions, affected-story discovery, previews) and testing (`test-run`) toolsets. The docs toolset requires a generated components manifest: current support covers React frameworks, Angular-Vite, and Vue3-Vite with its additional docgen flag; other frameworks may still use dev/test tools but **not** docs grounding. Tests require the Vitest addon; accessibility findings require configured a11y/axe tests. The experimental Codex/Claude plugins additionally provide init/setup/stories/upgrade skills and a Storybook CLI route to the tools. For an existing 10.x Storybook, prefer the documented MCP addon rather than upgrading merely to get plugin skills.

**Safe adoption:** install the official addon with `npx storybook add @storybook/addon-mcp` after reviewing the package/version and lockfile; enable `features.componentsManifest`, run Storybook locally, then register `http://localhost:6006/mcp` in the intended agent. In project instructions require querying docs before using component props, writing stories for meaningful error/loading/disabled/responsive states, and running the relevant tests. Inspect `/manifests/components.html` for omissions, stale examples and docgen warnings; JSDoc and stories determine what the agent sees. Prefer a pinned, reviewed package over unexamined `@latest` in autonomous execution.

**Failure/security boundaries:** a documented April 2026 issue reports OOM/timeouts with ~460 stories and TypeScript docgen; it is one reported deployment, not a proven universal regression. Trade docgen detail against startup cost and check current release behavior. ### Contrast-checking skills: WCAG 2 conformance is not an APCA verdict (reviewed 2026-10-23)

**Decision:** Keep the WCAG 2.2 contrast calculation as the release/conformance gate; APCA can be a *supplemental, experimental readability signal* for text size, weight and polarity. Never claim that APCA is the adopted WCAG 3 contrast algorithm: the [10 September 2026 WCAG 3 Working Draft](https://www.w3.org/TR/2026/WD-wcag-3.0-20260910/#text-contrast-sufficient-minimum) explicitly says the algorithm is **undetermined**. WCAG 3 is still a draft. Avoid treating either a single numerical score or a skill's PASS label as proof of real-world readability.

**Two inspected agent capabilities, neither a default install recommendation:**

- [`alikimovich/apca-cli`](https://github.com/alikimovich/apca-cli) (v0.1.0 in inspected `package.json`) is a small Node/Bun CLI plus Claude Code skill/Codex instructions. `src/check.ts` calls upstream `apca-w3`'s `calcAPCA` and `fontLookupAPCA`; `src/wcag2.ts` independently calculates WCAG 2 ratios, with the correct **24px regular / ~18.67px bold** large-text boundary. `--wcag2 --format json` can report both measures and disagreement, useful in a design-token review. **Not recommended for unattended installation or authoritative audits:** its README, package description and skill incorrectly state that APCA is what WCAG 3 is built on; the skill instructs agents to *side with APCA* when it disagrees with WCAG 2. The installer may fetch/install Bun, install packages or clone a moving `main`, reset its local clone, and append instructions to the user's global `~/.codex/AGENTS.md`. The skill contains a developer-specific fallback path (`/Users/panda/dev/apca-cli`). The wrapper's MIT declaration does not erase the [upstream APCA-specific licensing and maintenance terms](https://github.com/Myndex/SAPC-APCA/blob/master/LICENSE.md). Prefer **manual review of a pinned revision**, isolated installation, and explicit WCAG 2 precedence; never pipe the installer directly to a shell in an autonomous agent run.
- [`jakubkrehel/oklch-skill`](https://github.com/jakubkrehel/oklch-skill) provides useful OKLCH palette/gamut/Tailwind reference material, but its inspected `accessibility-contrast.md` reverses APCA's **signed polarity** (the canonical convention is positive for dark text on light background), gives **18px regular / 14px bold** as WCAG's large-text *pixel* boundary (the normative values are **18pt / 14pt bold**), and presents fixed `|Lc|` thresholds and an adjust-lightness-only rule too broadly. Its `SKILL.md` also treats APCA as the default and universal hex-to-OKLCH migration as a fix. **Do not install as an unquestioned contrast authority**; reuse specific color-space explanations only after validating them against standards and actual rendered colors.

**Agent workflow:** (1) identify *rendered* foreground/background pairs for each semantic token, theme and state (including overlays, opacity, gradients and images); (2) verify WCAG 2.2 SC 1.4.3: **4.5:1 normal text, 3:1 large text**, and SC 1.4.11: **3:1** for necessary non-text control/graphic cues; do not round borderline ratios upward; (3) optionally compute signed APCA Lc with a vetted implementation as a second lens, not a substitute pass/fail; (4) inspect the actual font, weight, text size, antialiasing, gamut and light/dark rendering; (5) run browser-based axe checks and human/assistive-technology review for contexts automation cannot resolve. `axe-core` itself [does not run its color-contrast rule in JSDOM](https://github.com/dequelabs/axe-core), and a [2026 OKLCH parsing issue](https://github.com/dequelabs/axe-core/issues/5036) is a report to reproduce/version-check, not grounds to discard all automated testing.

**Validation before promotion:** pin versions; independently calculate known pairs (including `#767676` on white, both polarities, near-threshold pairs, transparent layers and P3/OKLCH); check the installed skill's instructions, license and dependencies; compare outcomes against browser-rendered WCAG checks and manual readability review. No controlled comparison or broad adoption evidence was established here.

## Visual-to-source feedback tools: React Grab versus Agentation (reviewed 2026-10-23)

**Decision:** distinguish *locating the source of a rendered element* from *capturing a reviewer's design intent*. A browser-to-source hint can reduce code search, but neither tool validates design quality, accessibility, or a successful fix. Use the lightest handoff that preserves human review; automatic code-changing loops are an additional, separate permission decision.

| Dimension | React Grab (`aidenybai/react-grab`) | Agentation (`benjitaylor/agentation`) |
|---|---|---|
| Best-fit job | Select a rendered element and copy React component/source context to Claude Code, Codex or another agent; optional continuous clipboard watcher | Annotate elements, selected text or regions with a human's intended change; copy structured feedback or sync a review/response lifecycle through MCP |
| Actual mechanism | React/component stack and source-location hints from browser selection; `skills/react-grab/SKILL.md` uses `npx react-grab@latest pull` in a persistent watcher | React 18+ toolbar with DOM selectors, source hints, comment, severity and optional styles; localStorage by default, optional `agentation-mcp` stdio + HTTP bridge (nine documented tools) |
| Setup | `npx grab@latest init`; for Vite, dev-only `import("react-grab")`; Next.js README also shows a dev-gated unpinned CDN script, which should be replaced with a reviewed/pinned package path where possible | `npm install agentation -D`, dev-gated `<Agentation />`; for sync configure `claude mcp add agentation -- npx -y agentation-mcp server` **and** `<Agentation endpoint="http://localhost:4747" />`. Optional setup skill: `npx skills add benjitaylor/agentation` |
| Boundaries | Primarily React/dev source context; clipboard watcher must run on browser's machine, not remote agent host; source mapping depends on framework/build | React 18+, desktop-oriented; open shadow roots and same-origin frames supported, closed/cross-origin not; MCP server adds native `better-sqlite3` and local HTTP configuration |
| License | MIT | PolyForm Shield 1.0.0: free internal use per vendor, but restricts competitive products/services and redistribution obligations; **not equivalent to MIT** |

**Evidence worth retaining, with a critical boundary.** The maintainer-associated [React Bench](https://github.com/millionco/react-grab-bench) supplies a reproducible *source-file retrieval* harness rather than just promotional screenshots. Its README reports 330 synthetic Next.js cases, one Claude Sonnet 4.6 run per case: baseline 86% correct / 45.1 s geometric-mean resolution; React Grab 96% / 20.7 s; Agentation 96% / 31.5 s; Cursor Browser 95% / 30.7 s. It uses a 120-second penalty for incorrect answers, coupling speed and accuracy. The product's [benchmark page](https://www.react-grab.com/benchmarks) currently says **331** cases while the source README says **330**: record the exact evaluated revision before quoting results. The study is vendor-associated, uses a self-contained reproduction corpus and one model/trial, and measures **finding a file**, not correct UI repair, reviewer comprehension or accessibility. It is useful directional evidence, **not independent proof of “2× better design”**.

**Observed exceptions and failure modes.** React Grab [issue #417](https://github.com/aidenybai/react-grab/issues/417) describes owner-stack paths resolving to generated/virtual Webpack/Rspack modules instead of original source; [issue #215](https://github.com/aidenybai/react-grab/issues/215) reports a Next.js internal path prefix that breaks editor navigation (reported on older versions; re-test current releases). A file:line hint must be checked against the actual working tree before editing. Agentation [issue #173](https://github.com/benjitaylor/agentation/issues/173) documents a real setup trap: healthy MCP configuration without the `endpoint` prop, or missing the `server` subcommand, produces no usable sync. Its current setup skill explicitly tests the *full annotation round trip*, which is a meaningful improvement over install-only instructions. Open [Agentation issue #218](https://github.com/benjitaylor/agentation/issues/218) also reports difficulty selecting disabled controls: visual annotation is not complete UI coverage.

**Security and workflow contract for agents:**

1. **Keep tools out of production bundles** unless deliberately gated for trusted review. These tools read live DOM and may capture text, selectors, component paths, screenshots or styles. Use synthetic accounts; review copied payloads before sharing with hosted agents. Do not assume “local-first” means copied/synced content stays private after the user sends it.
2. **Review installations.** `npx ...@latest`, third-party skills, MCP binaries and CDN scripts are executable supply-chain dependencies; inspect package/skill source, pin a tested version where possible and review config changes. The React Grab skill's continuous watcher reads the *machine clipboard* and explicitly preempts current tasks on new grabs; do not enable an always-on watcher or autonomous edits merely to get one source hint. Require an explicit standing task, change boundaries, test/review and stop behavior.
3. **Keep MCP transport scoped.** Agentation's HTTP server defaults to loopback port 4747; its [CORS/origin settings](https://www.agentation.com/mcp) allow broad local development origins unless configured. CORS is **not authentication**, and requests without `Origin` remain allowed. Avoid public binding, use exact allowed origins where applicable, and do not expose annotated sensitive data through webhooks or remote tunnels.
4. **Verify the right thing.** For source lookup, check the suggested file exists and contains the intended component. For feedback sync, add a uniquely named test annotation and read the same text/page through MCP; a green `doctor` check alone is insufficient. For each requested fix, assert the intended state, run functional/accessibility checks and visually inspect the result before marking resolved. Agentation's critique/self-driving examples target several annotations; never manufacture findings to meet a quota.

**When not to install:** one-off edits where a screenshot + route + element description already identifies the source; non-React or mobile-native projects; highly sensitive authenticated interfaces without safe fixtures; projects where license terms prohibit redistribution; and automated loops without human-reviewed edit boundaries. Alternative: browser devtools/React DevTools plus `rg` and a screenshot; Playwright/Storybook for reproducible state/behavior testing. **Promotion test:** on the same real application, compare baseline search, React Grab copy, Agentation copy and Agentation MCP for source-hit correctness, actual fix quality, reviewer-intent retention, false edits, accessibility regressions, setup friction, token/time cost and confidential-data exposure. Include ambiguous wrappers, wrong sourcemaps, disabled controls, clean/no-defect cases and remote dev environments.

**Primary evidence:** [React Grab repo/skill](https://github.com/aidenybai/react-grab), [React Grab skill source](https://github.com/aidenybai/react-grab/blob/main/skills/react-grab/SKILL.md), [React Bench methodology](https://github.com/millionco/react-grab-bench), [Agentation repo/license](https://github.com/benjitaylor/agentation), [Agentation setup skill](https://github.com/benjitaylor/agentation/blob/main/skills/agentation/SKILL.md), [Agentation install](https://www.agentation.com/install), [Agentation MCP](https://www.agentation.com/mcp), [Agentation output](https://www.agentation.com/output). Source and docs inspected 2026-10-23; no independent experiment run.

## Rendered verification: separate the jobs

1. **Visual regression:** did an approved baseline change unintentionally?
2. **Reference parity:** does implementation match a specified design/reference?
3. **Rendered visual QA:** does the real state exhibit responsive, visual or journey defects?
4. **Design critique:** is the direction itself appropriate, coherent, distinctive and usable?
5. **Visual decision sandbox:** can a human cheaply express token, copy and element-level preferences before implementation?
6. **Persistent design memory:** did the agent actually consume the project's declared visual contract before editing?

Pixel similarity is not UX quality. A perfect reproduction can preserve a bad design; an intentional improvement can correctly fail regression. A sandbox preview is not evidence that the real application renders equivalently. Contract consumption is not evidence that the contract is good or current.

Explicitly exercise dark/light, 320–400% zoom, keyboard focus, empty/error and critical dialogs where applicable. ARIA snapshots are extra billable captures, not accessibility certification.
- **Baseline authority is a consequential write.** The review skill includes `argos review create --event approve|reject`, screenshot comments and `change ignore`; approval makes a build *eligible* for future baseline selection, not an immediate overwrite ([upstream baseline notes](https://github.com/argos-ci/argos-javascript/blob/main/skills/argos-pr-review/references/baseline.md)). Default agents to **read-only** `projects:read` MCP or project-token CLI; do not supply a broad personal access token merely to inspect. Explicit human review should own approvals, ignores and other mutations. The companion `argos-cli` skill covers project/team/automation administration too: its breadth is **not** a reason to grant those permissions.
- **Supply-chain/data boundary.** Pin/inspect the install source and dependencies before `npx skills add argos-ci/argos-javascript@argos-pr-review` or `@argos-cli`; install the Playwright SDK separately (`npm i -D @argos-ci/playwright`) only when a visual CI service is warranted. The reporter uploads screenshots, failure traces and optional ARIA text: use staging fixtures, redact sensitive content *before capture*, avoid authenticated production/user data and verify organization retention/access policies. Masking for diff stability is not a general privacy guarantee.

**Agent workflow gate:** (1) establish deterministic CI fixtures and explicit UI-state assertions; (2) capture named states/viewports and confirm default-branch baselines exist; (3) inspect *all* changed/removed/added snapshots, images and test metadata against PR intent; (4) classify intentional/regression/uncertain, reproducing uncertain diffs instead of suppressing them; (5) post a **read-only evidence report** with links and exact affected states; (6) request human approval for any baseline-affecting decision. Compare against Playwright-only and Chromatic on seeded real regressions *plus clean controls*, measuring missed defects, false alarms, inadvertent approvals, masked errors, time, token cost and sensitive-data exposure. **Evidence boundary:** upstream source and docs inspected 2026-10-24; no independent agent-quality benchmark or security audit.

## 2026-10-07: `ryktara/design-engineering-skill` — unusually strong evaluation discipline, but precision/recall failure is the lesson

**Status:** high-value research reference and promising context-first specialist; do not promote to the default stack as a general design authority yet.

This Claude Code skill is materially different from catalog-style design packs. It inspects the real repository first, classifies project evidence as KNOWN / INFERRED / UNKNOWN, derives task/platform/mode requirements, retrieves a small guidance bundle from a hand-written ontology, preserves detected design decisions by default, and verifies by rendering. The runtime is local Python 3.10+ standard library with no network/packages; the repository is MIT licensed. This is a comparatively narrow supply-chain surface, though the agent still executes local inspection/retrieval scripts and any later browser/emulator verification has its own trust boundary.

The strongest reason to study it is **negative evidence published by the maintainer**. Phase 6 pre-registered thresholds before its blind held-out set and retained failures rather than tuning the bar after results. On 525 held-out prompts, candidate c4 met only **5/11** thresholds: false-platform assignment (0.025), platform correctness (0.772), mode (0.92), forbidden concepts (0.049) and wrong-screen defects (0.072) passed, while critical-concept recall (0.448), required recall (0.35), human GOOD+PARTIAL (0.72), BAD (0.28), generic defects (0.137) and the pre-registered scope metric failed. Its implemented 32-task/16-codebase round helped 22 tasks and hurt none, but still failed 4/9 gates. The repository therefore labels itself **personal-production-ready, not stable-candidate**.

The durable finding is architectural, not a recommendation to install: **precision-first retrieval can make an agent safer and less generic while simultaneously starving it of necessary guidance**. The project reduced wrong-screen/forbidden contamination, but recall fell across historical held-out sets and 78 v5 cases returned empty bundles. Missing critical concepts dominated PARTIAL/BAD reviews. For design-agent tooling, measure abstention/empty-bundle rate and critical guidance recall alongside false positives and context size; “no guidance beats wrong guidance” is not universally true when a task has common but unstated design obligations.

Its evaluation method is also worth borrowing: freeze candidate hashes; pre-register thresholds; separate development/regression/held-out sets; use independent generation/review sessions; route defects to the earliest wrong layer; retain failed gates; and distinguish deterministic retrieval metrics from implemented-project outcomes. A particularly useful caution is disclosed by the project itself: all held-out generator/reviewer roles were Anthropic Claude sessions, so independence of sessions is not cross-vendor/model independence.

**Best fit:** study or controlled trial when project-context inspection, platform/input-modality discrimination and compact retrieval are more valuable than broad aesthetic ideation. It is especially relevant to multi-platform products where wrong web/mobile/TV assumptions are costly.

**Do not infer:** stable generalization, broad aesthetic superiority, cross-model portability, or causal design uplift from the current evidence. Its own strongest evaluation falsifies those stronger claims.

**Promotion gate:** compare against baseline and existing recommended skills on the same real projects, with critical-concept recall, empty guidance, wrong-platform/wrong-screen guidance, rendered quality, functional regressions and context cost all scored. Preserve its willingness to fail pre-registered gates rather than relaxing thresholds after the fact.

## 2026-10-07: OpenAI Skills API makes the trust boundary explicit

OpenAI's current Skills documentation adds an important correction to skill evaluation: a skill is not merely prompt text. In the Responses/Agents runtimes it can be a **versioned bundle of instructions, scripts, references and assets** copied into an execution environment. Discovery exposes only `name`, `description` and `path`; the model then decides whether to load the full instructions. The more consequential finding is security. - **pin the evaluated artifact, not only the repository name.** Hosted OpenAI skills have explicit versions and `default_version`/`latest_version` pointers; reproducible evaluation should record the exact version or commit rather than silently following latest;

**Five specific traps in the primary source (not hypothetical):**

1. **Keyboard false positive:** `command.md` says interactive elements need `onKeyDown/onKeyUp`. Native `<button>` and links already provide keyboard activation; custom key handlers are for custom widgets or additional shortcuts, not a universal requirement. W3C APG explicitly distinguishes native controls from ARIA-created widgets.
2. **Accessible-name false positive:** it insists icon buttons need `aria-label`, although a valid name can also come from `aria-labelledby` (or meaningful button content). Review the computed accessible name, not one attribute's presence. Similarly, `role="status"` already implies polite live announcements; `aria-live="polite"` is not universally required on every toast.
3. **Contradictory zoom guidance across Vercel's own documents:** the full guidelines README suggests `maximum-scale=1` as an alternative to a >=16px mobile input font, **then says never disable zoom**; the condensed `command.md` explicitly flags `maximum-scale=1` as an anti-pattern. Reject the restrictive viewport workaround; preserve zoom and test mobile focus/keyboard behavior.
4. **Performance category error:** the checklist groups “>50 items: virtualize” with `content-visibility: auto`. The latter can skip offscreen **rendering** while keeping content in the DOM/accessibility tree; it is not DOM/window virtualization. Choose pagination, containment or virtualization based on measured cost, content discovery, focus and assistive-technology behavior, not a universal 50-item cutoff.
5. **Context-free defaults:** mandatory `font-display: swap`/font preload conflicts with role- and network-dependent font loading; “deep-link all stateful UI” is too broad for ephemeral hover/draft state; `beforeunload` is unreliable on mobile and may affect Firefox bfcache. Treat these as review questions, not unconditional fixes. The checklist also mixes editorial taste (Title Case, curly quotes) with accessibility requirements, so findings need severity and evidence labels.

**Safe workflow:** install **only this skill** via the official skills CLI (`npx skills add vercel-labs/agent-skills --skill web-design-guidelines`) after reviewing the installer, or copy its single `SKILL.md` into a project-approved skill location. The runtime fetch of `command.md` is a separate **remote-instruction trust boundary**: review/pin an audited revision or vend a local snapshot for reproducible/offline/sensitive work; never treat a newly fetched checklist as higher authority than repository rules, WCAG, or user constraints. The skill file itself declares no scripts/dependencies, but a CLI install can execute installer/package code; inspect separately. Its parent README declares MIT; verify downstream redistribution terms for copied guideline content separately.

**Where it fits:** run after implementation as a *triage pass*; require each finding to include observed code, affected behavior, applicable standard (or label as heuristic), severity and a falsifiable verification step. Confirm with keyboard, screen reader, browser/Playwright, responsive and performance checks. Use Chrome's `modern-web-guidance` for targeted browser implementation references, Storybook MCP for actual component contracts, and Playwright/axe/manual AT for rendered checks. None alone certifies accessibility or design quality.

**Promotion test:** seed native buttons with no keydown handler, icon buttons correctly named by `aria-labelledby`, `role=status`, a 60-item cheap list, a genuinely expensive 30-item list, a `maximum-scale=1` page, and a broken keyboard custom widget. Compare skill vs no-skill for verified findings, false positives, missed failures, regression-inducing “fixes”, tokens and elapsed time. Do not promote based on stars or checklist length.

## Open evidence gap

Evidence is much stronger for **what skills contain** than for **how much they improve output**. Build a repeatable benchmark: identical brief + starter repo + baseline agent versus one skill versus composed skills, then blind/rubric rendered evaluation. For Codex-native harnesses, preserve model/version and delegation behavior because syntactic compatibility does not imply behavioral equivalence. For verification skills, seed known responsive/state/visual defects and measure detection, false positives, missed states, time/context cost and whether captured evidence is actually opened and reasoned about. For decision sandboxes, measure whether structured visual feedback reduces clarification turns and implementation churn without increasing divergence from the real app. For persistent design-memory wrappers, measure whether they reduce contract violations beyond what ordinary project instructions already achieve. Popularity, activation rates and attractive before/after examples are weak proxies for causal value.
