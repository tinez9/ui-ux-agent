# UX Patterns

Reusable interaction patterns and their tradeoffs. Prefer task-oriented guidance over component catalogs.

## Forms: validation and error recovery

Treat a form as a sequence of user decisions, not a collection of inputs.

### Native customizable selects: displayed and submitted values can diverge (2026-10-25)

**Decision:** Start with a labeled native `<select>` for a single choice. If a richer option layout materially helps (status icon, color swatch, brand-specific hierarchy), progressively opt in with `appearance: base-select` on **both** the select and `::picker(select)`; retain the classic select fallback. Chromium 135+ and Safari 27 ship the customizable dropdown; Firefox had not shipped it as of 2026-10-25. Unlike the classic select, the picker stays in the browser viewport and does **not** use the mobile OS picker. This tradeoff is not an automatic usability win. Do not assume customizable multi-select/listbox support matches the single-choice dropdown.

**Data and accessibility contract:** Give each `<option>` human-readable text, mark decorative icons `aria-hidden="true"`, and set an **explicit stable `value`** for options with icons, translations or mutable labels. `aria-hidden` does **not** remove icon characters from `textContent` or the default form value. For example, `<option value="basic"><span aria-hidden="true">★ </span>Basic</option>` submits `basic`; without `value`, it can submit `★ Basic`. Keep a real label on the select. Do not put buttons or links inside options: the spec disallows them, and WHATWG #12328 still discusses inconsistent browser handling. The optional first-child `<button><selectedcontent></selectedcontent></button>` is inert, **not** an action slot.

**Dynamic clone trap:** `<selectedcontent>` contains a **clone** of the selected option, not a live binding. Editing the selected option's label in place does not refresh the closed control; changing selection does. Without an explicit value, the submitted value can update while the closed control shows the old label. Prefer stable option data; when a selected label changes, explicitly synchronize the displayed clone or use the simpler native selected-text rendering. Verify framework rerenders and SSR hydration rather than assuming React/Vue automatically repair the clone.

**Reproduction (three repeated isolated runs, 2026-10-25):** Playwright Python 1.57 / Chromium 144.0.7559.96, with `base-select` and `selectedcontent`. Changing selected option text `Basic` → `Basic changed` left `selectedcontent` showing `Basic`; selecting another option refreshed it. With no explicit option value, changing `★ Basic` → `★ Renamed` updated `FormData` to `★ Renamed` while the closed control still displayed `★ Basic`. With `value="basic"`, submitted data remained stable despite label mutation. This is a **single-engine DOM fixture**, not cross-browser, AT, mobile or user-outcome validation.

**Agent QA gate:** Compare classic fallback with the enhanced picker in Firefox, Safari, Chromium and mobile; test keyboard/focus, real screen-reader names, zoom/forced colors, RTL, text-only options, localization, form serialization, selected-option mutation, hydration, and invalid interactive descendants. A successful `CSS.supports()` check or attractive screenshot is not accessibility certification.

**Primary evidence:** [MDN guide](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select), [MDN selectedcontent cloning](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/selectedcontent), [Chrome tradeoffs](https://developer.chrome.com/blog/a-customizable-select), [WebKit text-label rule](https://webkit.org/blog/18117/the-golden-rule-of-customizable-select/), [Safari 27](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/), [WHATWG #12328](https://github.com/whatwg/html/issues/12328).

### Implicit Enter submission is form-scoped, not last-field-only (2026-10-25)

The HTML Living Standard defines a form's **default submit button** as the first submit button in tree order associated with that form. On platforms supporting implicit submission (often Enter in a single-line input), the browser activates that button even if focus is on the **first** of several text fields. If there is **no** submit button, implicit submission is blocked when more than one qualifying single-line input belongs to the form; with at most one such input it can submit without a submitter. A disabled default button blocks implicit submission even when a later enabled submit button exists. Enter in a textarea normally inserts a newline; a Ctrl/Cmd+Enter send shortcut is an *application choice*, not a built-in HTML rule.

**Agent implementation contract:** use a semantic `<form>` with an intentional `type="submit"` default action, give non-submit controls `type="button"`, handle the form's `submit` event (and `SubmitEvent.submitter` for multiple actions), and let native constraint validation work. Do not add blanket Enter `preventDefault()` handlers or make only the last field submit based on a copied design-rule slogan. For multi-action forms, check that the **first** submit button is the safe, expected default; do not accidentally make Delete the implicit action. Preserve textarea composition/IME behavior and keyboard alternatives.

**Falsification:** an isolated Playwright keyboard probe on Chromium 144.0.7559.96 observed Enter from **both** inputs activate the first Save submitter when two text inputs and Save/Delete submit buttons were present; neither input submitted with two fields and no button; one field/no button submitted with no submitter; a disabled first submitter prevented submission; textarea Enter inserted a newline while the adjacent single-line input submitted. This is a single-engine behavioral check, **not** cross-browser/assistive-technology validation. It contradicts a literal reading of the "last control" advice copied from Vercel into a third-party UI-rule corpus; that advice is a design heuristic, **not** the platform's implicit-submission algorithm. Sources: [WHATWG HTML](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#implicit-submission), [MDN submit event](https://developer.mozilla.org/en-US/docs/Web/API/HTMLFormElement/submit_event), [Vercel guidelines](https://vercel.com/design/guidelines).

### Reduce work before optimizing messages
- Ask only for information needed for the task.
- Prefer removing a field over polishing it. Baymard's checkout research finds field count can matter more than step count; treat this as commerce evidence, not a universal numeric rule.
- Hide uncommon optional inputs behind a clearly named reveal only when most users do not need them.
- Keep persistent visible labels and put constraints, examples, and reasons for unexpected requests near the relevant field.

### Be tolerant before declaring an error
Accept or normalize harmless format variation when the input remains unambiguous. Validation should reject information because the system cannot safely use it, not because it differs cosmetically from a preferred format. Server-side validation remains authoritative.

### Choose validation timing by the cost of delayed feedback
Do not default to errors on every keystroke or blur. For ordinary forms, let users finish input and validate on attempted progression/submission. Earlier feedback is justified when waiting creates meaningful wasted work, such as a character limit or safely checkable constraint. Asynchronous facts need explicit pending/success/failure states.

### Make errors recovery instructions
When an error is detected:
- identify the affected field in text, not color alone;
- explain what is wrong or what acceptable input requires;
- suggest a correction when one is known and safe;
- reuse language from the field label;
- preserve entered values unless security requires otherwise;
- avoid blame, generic "invalid input", or clearing the form.

For multiple errors, combine field-local messages with a summary that links to affected fields. Deliberately manage focus after failed submission.

### Accessibility contract
- Programmatically associate labels, hints, and error descriptions with controls.
- Meet WCAG 3.3.1 by identifying/describing detected errors in text.
- Provide correction suggestions where known and safe (WCAG 3.3.3).
- Do not rely on color, iconography, or border treatment alone.
- Use correct semantic input/autocomplete metadata for personal-data fields where applicable.
- Expose dynamic validation/status changes accessibly without noisy announcements.

### Progressive disclosure is conditional
Hide an optional field/section when most users do not need it and the reveal clearly names it. Keep it visible when discovery failure is costly or many users need it.

### Implementation checks
Test keyboard-only recovery, screen-reader error order, zoom/reflow, mobile keyboards, autofill, paste/equivalent formats, server failures, stale async validation, data preservation, first-error navigation, repeated submission, slow networks, and localization.

## Native disclosures and exclusive accordions: group scope and focus are product decisions — 2026-10-25

**Choose disclosure before exclusivity.** First test whether content should be hidden at all: important instructions, frequently needed information and sequential tasks are usually better visible under headings. For optional short explanations use native `<details><summary>Clear question</summary>…</details>`. For a multi-section accordion, prefer independent disclosures when users may compare answers, keep several sections open or use “show all”. Add the same nonempty `name` to sibling `<details>` elements **only** when opening one should close another; this is an *at-most-one-open* contract, not a required-one-open tab set. GOV.UK's accordion permits several sections open, unlike a native exclusive group. Avoid nested disclosures/accordions as a default.

**Critical component-composition trap:** per WHATWG HTML, a details name group includes **every matching nonempty `name` in the same DOM tree**, even in unrelated sections; a wrapper, React component boundary or physical distance does **not** isolate it. Generate a stable, unique group name for each accordion instance (and keep it stable across SSR/hydration). Shadow roots are separate trees, not a recommended workaround for ordinary name collisions. Never nest an element in another `<details>` with the same group name. HTML forbids authoring two initially `open` members of the same group; `open="false"` still means open because `open` is Boolean. Browser enforcement mutates the other member's `open` attribute; do not maintain competing independent “controlled” open flags that can disagree with the DOM.

**Interaction and accessibility contract:** use a meaningful `<summary>` as the first child and preserve its visible keyboard focus and native marker or an equally clear replacement. Native summary activation supports Enter/Space; do not demand the optional Arrow-key navigation from the *custom* WAI-ARIA APG accordion pattern of a plain native disclosure. Use surrounding headings/sections to express information hierarchy; a visual title alone does not guarantee a heading in the accessibility tree. The `toggle` event fires **after** state changes and can coalesce rapid transitions; read actual `details.open` for the resulting state, not as an audit trail of every intermediate state. If application logic closes a panel containing focused controls, explicitly manage focus to a visible, meaningful target and preserve any unsaved input.

**Isolated falsification (Chromium 144, Playwright Python, 2026-10-25):** two independent `<section>` widgets using `name="shared"` unexpectedly closed each other's panel; opening a matching item inside a shadow root did **not** close the light-DOM item. Rapid script-driven changes produced coalesced `toggle` events. Opening another member **programmatically** while focus was on a button in the closing panel left `document.activeElement` on that now-hidden button until subsequent Tab. This is one headless-engine observation, **not** a proven cross-browser/AT defect or evidence that normal user activation always strands focus. Native summary Enter and Space worked in the same engine.

**Agent regression gate:** mount two independent instances with deliberately colliding names as a negative control, then verify unique-name isolation, initial open markup, dynamic insertion, keyboard/visible focus, programmatic close while focus is inside, zoom/forced colors, browser find-in-page, unsaved forms, no-JS fallback, and screen-reader heading/state navigation on real target engines. Compare independent versus exclusive versus always-visible content on the actual task; reduced height alone is not a user-outcome metric. Sources: [WHATWG HTML](https://html.spec.whatwg.org/multipage/interactive-elements.html#the-details-element), [MDN details](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/details), [W3C APG accordion](https://www.w3.org/WAI/ARIA/apg/patterns/accordion/), [GOV.UK accordion](https://design-system.service.gov.uk/components/accordion/), [GOV.UK details](https://design-system.service.gov.uk/components/details/).

**Animated-close exception (tested 2026-10-26):** CSS transitions on `::details-content` can leave a logically closed panel **visually and keyboard-interactive** until exit finishes. In Chromium 144, Tab entered a nested button during a 900ms `content-visibility ... allow-discrete` close, then focus dropped to BODY when the transition ended (3/3 fresh fixtures); native instant close skipped it. Prefer instant close for interactive disclosures; if exit motion is justified, synchronize descendant inertness and focus with logical closure, not merely CSS completion. See [disclosure exit-motion reproduction](INTERACTION_MOTION.md#native-disclosure-exit-motion-can-outlive-keyboard-state--tested-2026-10-26). This does not establish Safari/Firefox or screen-reader behavior.

### Searchable disclosures versus hidden application state (2026-10-25)

For content users may search with Ctrl/Cmd+F or reach by fragment, prefer a meaningful native `<details><summary>` where suitable; the HTML Standard specifies find-in-page access to closed disclosures. Custom `hidden="until-found"` exposes text to browser find/fragment revealing (`beforematch` → remove `hidden` → scroll), but **not** to permission-gated secrets or as a generic replacement for proper tabs/inactive routes. It differs from author CSS `content-visibility: hidden`. Its container still generates a box (margins/borders/padding may remain), and `display: none`, `contents` or `inline` prevents automatic reveal. Keep decoration on inner content, synchronize `aria-expanded`, focus and application state after browser-initiated opening, and avoid framework rerenders that immediately close the matched section.

**Support is not one Boolean:** web-features data reviewed 2026-10-25 lists Chromium 102+ and Firefox 148+ but no Safari for `hidden="until-found"`, while the WHATWG developer summary still says Chrome-only. MDN labels the *`beforematch` event* Baseline 2025; that does **not** prove the full attribute/find-in-page workflow is interoperable. `'onbeforematch' in HTMLElement.prototype` is a weak proxy, not a functional acceptance test. Provide a visible/readable fallback for unsupported browsers and verify actual find-in-page, fragment links, CSS display overrides, keyboard/screen readers and independent widget instances on supported targets. Evidence: standards/docs and a source-audited agent skill; **no live browser/AT reproduction in this cycle**. Sources: https://html.spec.whatwg.org/multipage/interaction.html ; https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/hidden ; https://web-platform-dx.github.io/web-features-explorer/features/hidden-until-found/ ; https://developer.chrome.com/docs/css-ui/hidden-until-found .

## Native dialogs: dismissal is a state/consent policy, not a modal styling option — 2026-10-25

**Decide modality first.** Use `dialog.showModal()` for a task that must block background interaction (browser top layer, inert background, contained Tab sequence); use `dialog.show()` only when the rest of the page must remain interactive. A bottom-sheet visual shape does **not** by itself imply modal semantics. Give the dialog a meaningful accessible name, an explicit visible close/cancel route, appropriate initial focus, and a predictable focus destination when dismissed. Large content should keep its beginning and focused control visible, including at zoom/mobile keyboard sizes. Do not manually remove `open` from a modal: WHATWG warns this can leave the document blocked without the normal close event.

**Choose the close policy independently.** `closedby="any"` enables outside-click/tap light dismiss **and** platform close requests; `closerequest` allows platform requests (e.g. Escape) but not backdrop light dismiss; `none` requires a developer close mechanism. The missing/invalid default is `closerequest` after `showModal()` but `none` after `show()`. Contrary to the GoogleChrome modern-web-guidance guide's blanket “DO NOT” for non-modal dialogs, `closedby="any"` also light-dismissed a **non-modal** `show()` dialog in a controlled Chromium test, despite there being no modal `::backdrop`. It is therefore wrong to equate light dismiss with modality. **Support gate:** `closedby` remains non-Baseline in October 2026 (Chrome 134+, Firefox 141+, no Safari/iOS Safari per web-features); do not make outside-dismiss the sole way to escape a sheet. For portable non-modal popover behavior, consider `popover="auto"` and its distinct semantics/stacking, rather than assuming all dialogs are interchangeable.

**Protect in-progress work at the event boundary.** `requestClose()` triggers cancelable `cancel` before `close`; `close()` and a successful `method="dialog"` submission bypass that cancellation path. If discarding a draft requires confirmation, block the request synchronously with `cancel.preventDefault()` and offer an explicit discard/save decision. Never interpret `close` as a pre-dismiss veto. Do not auto-close an async save dialog merely because a form was submitted; wait for authoritative acceptance or show recoverable pending/failure state. Avoid mutating `closedby` inside `cancel`: WHATWG issue #12482 documents a spec/engine disagreement, and Chromium reproduced a non-modal `requestClose()` leaving the dialog open when its handler removed `closedby` (even without `preventDefault()`). Use stable close policy and explicit application state instead.

**Controlled falsification (2026-10-25):** Linux Chromium **144.0.7559.96**, Playwright Python, nine isolated `page.set_content` cases repeated **three times each** with identical results. Outside click kept default modal and default non-modal open, closed `showModal()+closedby=any` with `cancel→close`, kept `closedby=none` modal open, and closed `show()+closedby=any` with `cancel→close`. For non-modal `show()+closedby=any`, removing `closedby` in `cancel` caused `requestClose()` to emit only `cancel` and leave it open; the same mutation on modal `showModal()` emitted `cancel→close`. `cancel.preventDefault()` blocked `requestClose()`, while `close()` bypassed it. This is a real **single-engine synthetic fixture**, not Firefox/Safari, OS Back, touch, real assistive technology, or a user-study result.

**Agent acceptance:** compare modal/non-modal/popover with `closedby` absent/`any`/`closerequest`/`none`; test outside tap, Escape, mobile Back, keyboard focus restoration, nested layers, dirty draft, save failure, validation and screen-reader announcement on actual supported engines. Seed an unsupported-Safari control and a cancel handler that changes `closedby`; assert the **final open state and persisted draft**, not just that a `cancel` event fired. Primary evidence: [WHATWG dialog](https://html.spec.whatwg.org/multipage/interactive-elements.html#the-dialog-element), [WAI-ARIA APG modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [MDN requestClose](https://developer.mozilla.org/en-US/docs/Web/API/HTMLDialogElement/requestClose), [web-features closedby](https://web-platform-dx.github.io/web-features-explorer/features/dialog-closedby/), [WHATWG #12482](https://github.com/whatwg/html/issues/12482).

## Numeric entry: identifiers, quantities and localized amounts are different contracts — 2026-10-24

**Choose the control from the meaning of the value, not whether it contains digits.** A numeric-looking identifier (account/reference/postal code, phone number) is a *string*: preserve leading zeros and exact digits; never coerce it through JavaScript `Number`. A count or bounded adjustable quantity may be a *number with meaningful steps*. Money, percentages and measurements are *quantities with units, precision and locale rules*, not just text to strip punctuation from.

### Input and keyboard decision
- **Identifiers:** a labeled `<input type="text">`, with appropriate `autocomplete` and, where useful, `inputmode="numeric"`. `inputmode` only hints at the virtual keyboard; it does **not** validate. Do not add `pattern="[0-9]*"` without considering non-Latin digits and the actual identifier alphabet. A postal code may contain letters.
- **Decimal entry without step controls:** a labeled text input with `inputmode="decimal"` is often more predictable than `type="number"`; show units in the label (e.g., “Weight, in kilograms”). **Exception:** GOV.UK's June 2026 guidance warns that some mobile decimal keyboards lack a minus key; for permitted negatives, test devices and consider ordinary `type="text"` without an inputmode hint rather than trapping users. Paste and hardware-keyboard entry must still work.
- **Genuine increment/decrement task:** native `type="number"` can be appropriate when spinbutton semantics and keyboard arrows are useful; configure `min`, `max` and `step` intentionally (`step` defaults to 1, so many decimals are invalid). Do not use it merely because data is numeric: implicit spinbutton behavior can change values through arrow/scroll actions, and browser filtering may conceal invalid characters instead of explaining them. The W3C spinbutton pattern defines keyboard semantics; avoid recreating it casually.

### Parsing, commit and precision contract
1. **Preserve the edit buffer.** Users need to enter intermediate states such as `-`, `1,` or an empty field without the UI rewriting the caret, snapping to a valid step, or replacing their text with the last saved value on every render. Distinguish *typed string*, *parsed candidate*, *validated quantity*, and *committed value*.
2. **Parse with an explicit locale and accepted-input policy.** `1.234,56` (de-DE) and `1,234.56` (en-US) have different grouping/decimal roles. `1,234` can be ambiguous across locales; do not guess by globally replacing commas or calling `Number(raw)`. `Intl.NumberFormat` **formats** but does not provide a general inverse parser. A localized field/parser must define grouping, minus signs, numbering systems, whitespace, copy/paste and invalid/ambiguous cases; display the interpreted value before a high-stakes commit.
3. **Keep display, unit and serialized value distinct.** Never infer the currency from a symbol alone; choose an explicit currency code and conversion/scale contract (e.g., percent UI vs fractional API). Validate range/precision on the server. JavaScript `Number` cannot exactly represent integers beyond `Number.MAX_SAFE_INTEGER` and cannot generally guarantee decimal monetary arithmetic; use bounded integer minor units or an appropriate decimal representation end-to-end when exactness matters.
4. **Avoid silent correction.** Clamping, rounding, and snapping on blur can alter a user's intended amount. Prefer an explained validation error for consequential values; use snapping only where step-based editing is an explicit task expectation.

**Library counterexample, not blanket endorsement:** Adobe React Spectrum's `NumberField` offers locale-aware number parsing, formatting, stepper controls and raw-number form submission, but its documented `onChange` is a **commit** event (blur/step), not a keystroke stream. Its default `commitBehavior="snap"` clamps/rounds to range/step on blur; `"validate"` is the alternative. `isWheelDisabled` can disable scroll-driven changes. A currently **open** React Aria issue (#9059, observed in 1.12.1) reports negative values becoming positive with `signDisplay: "never"` during decrement: a targeted regression fixture, not proof all versions fail. Do **not** repeat older issues as current bugs: the stale Enter-submit report (#9671) was closed via #9683, and the `formatOptions` reference-reset report (#1893/#9899) was closed via #9905. Verify the *installed* version and behavior.

**Agent QA fixtures:** test `0` vs empty; `-0.5`; trailing separator; leading zeros in IDs; `1,234` across en-US/de-DE; Arabic-Indic digits; paste with nonbreaking spaces; large safe/unsafe integers; `0.1 + 0.2` precision assumptions; min/max and non-unit step; negative input on iOS/Android; keyboard arrows, mouse wheel and touch scroll; screen-reader labels/value announcements; blur vs Enter submission; rerenders mid-edit; server rejection and round-trip reload. Include clean controls that should *not* be rewritten. Do not declare locale correctness from a formatted display alone.

**Evidence boundary:** GOV.UK's tested public-service recommendation and MDN/W3C semantics support the decision split; Adobe documents one library's contract, while GitHub issues are version-specific failure reports. This is implementation guidance, not an independent cross-browser, multilingual or assistive-technology benchmark.

**Primary sources:** https://design-system.service.gov.uk/components/text-input/ (June 2026 change log); https://technology.blog.gov.uk/2020/02/24/why-the-gov-uk-design-system-team-changed-the-input-type-for-numbers/ ; https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/number ; https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/inputmode ; https://www.w3.org/WAI/ARIA/apg/patterns/spinbutton/ ; https://react-spectrum.adobe.com/NumberField ; https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/MAX_SAFE_INTEGER .

## Consent and tracking preferences: visual choice is not runtime consent — 2026-10-23

**Decision:** model three separate contracts: **purpose/legal basis** (which storage or access actually requires consent in the applicable jurisdiction), **choice UX** (what users can knowingly accept, reject, change or withdraw), and **runtime enforcement** (what code, tags, storage and third parties actually do). A convincing banner cannot establish that consent was obtained or honored.

### Choice and scope contract

- **Classify each purpose before drawing controls.** Separate essential/exempt functionality, consent-requiring tracking, and any jurisdiction-specific opt-out exceptions. Avoid labeling advertising, cross-site profiling or multi-purpose tags “necessary” because they are useful to the business. Do not silently reuse one choice for a newly introduced purpose.
- **For consent-based non-essential uses:** offer understandable, readily accessible accept/reject choices and granular purpose settings. When an accept-all action is prominent, do not bury refusal behind a low-contrast paragraph link or extra friction; do not preselect consent switches. Closing, scrolling or continuing to browse is **not affirmative opt-in**. Keep labels specific to the effect rather than euphemisms such as “improve experience.” The EDPB Cookie Banner Taskforce found broad agreement against absent rejection on layers with acceptance, but its 2023 report is a **minimum coordinated enforcement position**, not a universal EU compliance certificate; national interpretation still matters.
- **Persist refusal as deliberately as acceptance**, without repeated prompts on every page. Offer a clearly findable way to reopen choices and withdraw consent with comparable ease. A six-month retention period for both acceptance and refusal is a **CNIL recommendation assessed case by case**, not a universal legal expiry.
- **Scope must be visible:** specify whether a preference applies to this browser/device, an account, or all signed-in devices. France's January 2026 CNIL cross-device guidance requires comparable scope/ease for acceptance, refusal and withdrawal when a service uses cross-device consent. Never imply that local-browser choice propagated to other devices if it did not.

### Important exception: do not copy one country's consent banner everywhere

The UK's **final ICO guidance of 29 April 2026**, following changes to PECR, recognizes narrowly conditioned *statistical-purpose* and *appearance/preference* storage-access exceptions with clear information and a **simple, free means of objecting**. An eligible exception may therefore use an initially enabled preference rather than prior opt-in. This is **not** permission for behavioral advertising, individual tracking, profiling, retained person-level analytics, or multi-purpose vendor scripts; it is not a statement of French/EU law. Other non-exempt purposes still require valid prior consent. Classify each technology by **actual purpose and data flow**, not by a generic “analytics” toggle.

### Agent implementation and adversarial checks

1. Create a purpose inventory: tag/script, storage or device access, recipient, data use, jurisdiction, exemption rationale, default state, withdrawal behavior and retention. Review with the responsible privacy/legal owner; this is a design/engineering checklist, **not legal clearance**.
2. On a clean browser profile, inspect cookies, local storage, network requests, pixels and third-party script initialization **before any choice**. A visible reject button is not enough if tracking already fired. Distinguish harmless asset requests from storage/access or personal-data transmission.
3. Repeat after **reject**, **accept**, **customize**, **withdraw**, reload, route change, new tab, sign-in/out, and (where implemented) another device. Check that rejected purposes do not restart via tag-manager defaults, delayed callbacks, race conditions or account synchronization. A preference receipt must not itself be mistaken for marketing consent.
4. Test keyboard, screen reader, narrow viewport, zoom, translated copy, focus restoration and an unavailable consent service. The page must not silently treat a CMP/network failure as acceptance.
5. Include counterexamples: genuinely necessary session state; narrowly eligible UK aggregate service analytics with an objection control; and a third-party analytics tag that also enables advertising (not eligible merely because its dashboard shows aggregate counts).

**Evidence boundary:** EDPB 2023 taskforce and 2023 deceptive-design guidance, CNIL 2026 FAQs/cross-device recommendations, and ICO's April 2026 final guidance establish regulator positions and important jurisdictional exceptions. They do not establish that any particular CMP implementation is compliant, or that this test plan has measured UX benefits. The runtime QA contract is agent synthesis; no instrumented CMP test or cross-jurisdiction legal review was performed.

## Settings save behavior: commit scope before choosing autosave — 2026-10-22

**Decision:** a settings page is not one transaction by default. Classify each change by **scope, consequence, coupling and reversibility** before choosing immediate application, per-field autosave, explicit Save, or draft persistence. Do not equate an instantly updated control with a server-confirmed preference.

### Choose the transaction boundary

- **Independent, low-risk, reversible preference** (theme, units, a local display option): immediate application can fit a switch/segmented control. Explain whether it applies **on this device, to this account, or across an organization**; preview locally if useful, but do not say “Saved” until the intended persistence succeeds. Give a recoverable failure path.
- **Coupled settings** (e.g. multiple notification rules, role permissions, integration credentials): edit as **one explicit transaction** with a named Save/Cancel boundary. Saving each field independently can persist an invalid or partially configured policy. Keep original values for Cancel; retain draft values and errors if Save fails.
- **High-impact or hard-to-reverse change** (visibility/privacy, security, billing, deletion, sharing scope): require deliberate activation and appropriate review/confirmation or reversal; do not autosave on an incidental control change. WCAG 3.3.4 offers **reversible, checked or confirmed** paths for covered consequential submissions; it does **not** demand a confirmation for every routine save.
- **Long-form draft**: autosave *draft progress* when losing work is costly, but label it “Draft saved”, not “Published” or “Applied”. Avoid silently persisting passwords, tokens, or sensitive draft data. Explicit publication remains a separate action.

**Why not a universal autosave rule?** First-party systems disagree: Microsoft Windows settings recommends immediately reflecting changes; GitHub Primer defaults to explicit saving for declarative form controls and instant saving for imperative switches; GitLab Pajamas allows per-input autosave in long forms with persistent inline failure/retry; Octopus Deploy deliberately prefers explicit Save for resource edits. These are context-specific product policies, **not** controlled evidence that one method wins universally. In particular, Primer warns that arrow-key exploration of radio/native-select options can unintentionally apply changes if selection immediately commits. Test the actual control/browser/AT behavior.

### Persistence, failure and accessibility contract

1. Track **displayed/draft value**, **pending write**, **confirmed persisted value**, **version** and **failure/conflict** separately. For optimistic changes, make the pending state legible; on rejection preserve the user's intended value for retry/reconciliation instead of silently reverting or endlessly claiming success. If retries are possible, handle timeout-after-commit and idempotency.
2. For account/team preferences edited in multiple tabs/devices, use server-side versioning or conditional updates (e.g. strong ETag + `If-Match`; conflict response `412`) to prevent silent lost updates. A per-field patch does not automatically solve cross-field invariants; the server owns validation/authorization.
3. Keep the save boundary discoverable: do **not** mix auto- and manual-save semantics **inside the same form**. If different independent sections behave differently, label that distinction clearly. A Save button should name its scope; an unchanged/invalid Save may remain focusable with explanation rather than be silently removed. Primer recommends keeping it enabled; Octopus disables unchanged Save—test discoverability and error recovery rather than universalizing either policy.
4. Use an inline **Saving… / Saved / Couldn't save — Retry** status near the affected section when the result is not otherwise obvious; keep failures visible until resolved. Avoid repeated toast storms and do not rely on a transient toast for a required retry or undo action. Use an appropriate status/alert announcement without moving focus unnecessarily.
5. **Autosave is not automatically a WCAG 3.2.2 violation**: that criterion concerns unexpected *changes of context*, not every content or persistence update. But selecting a preference must not unexpectedly navigate, move focus or substantially recontextualize the page without prior warning. Test keyboard selection and screen-reader browsing as well as pointer/touch.
6. Treat unsaved navigation, tab close, offline restart and cross-device conflict as **recovery problems**, not just confirmation-dialog problems. A `beforeunload` warning is best-effort; preserve recoverable drafts when justified and avoid storing secrets casually.

**Agent acceptance matrix:** independent switch vs coupled form vs sensitive setting vs long draft; pointer, keyboard/native-select arrows, screen reader, 400% zoom; save success, 500/timeout-after-commit, validation rejection, offline, two tabs/devices, rapid A→B→A toggles, navigation mid-write, stale response arriving after a newer write, cancel, and permissions changed by another actor. Assert what the user believes was saved against the server's actual state and scope.

**Evidence boundary (reviewed 2026-10-22):** design-system guidance demonstrates real competing product policies, not comparative task outcomes. W3C defines accessibility constraints; HTTP conditional-write documentation establishes a concurrency mechanism, not a complete synchronization strategy. The choice of transaction granularity and whether autosave improves success remain hypotheses for matched task tests.

## Passkeys and accessible authentication: preserve the complete sign-in path — 2026-10-15

**Decision:** a passkey is a phishing-resistant credential, **not** a complete sign-in/recovery experience. Optimize the journey from discovery → enrollment → sign-in → fallback → recovery → credential management, not just the happy-path biometric prompt.

- **Mixed password/passkey accounts:** keep a normal, labeled username/password form with password-manager autofill and paste. Add `autocomplete="username webauthn"` (the `webauthn` token last) to the username field and start WebAuthn `get({ publicKey, mediation: "conditional" })` only when supported. The browser may offer stored passkeys in its native autofill UI. **Do not hide password sign-in** or infer from an unresolved conditional request that the user has no passkey; the request can remain pending while the user chooses another credential. Offer a clear explicit “Use a passkey” route when appropriate, especially when autofill is unavailable or undiscoverable.
- **Passkey-only cohorts:** a dedicated “Sign in with a passkey” button can be simpler when the product knows all users have passkeys. For mixed cohorts, a passkey-only screen can lock out legitimate users. Cross-device authentication (phone/QR/proximity) is a useful supported route, not a guarantee that the user has another compatible device or working connectivity.
- **Enrollment:** explain the device/browser prompt *before* opening it and confirm registration only after the server accepts the credential. Offer creation after a trusted sign-in, in security settings, or after recovery; allow “Not now” without blocking unrelated work. Explain that the site does not receive fingerprints/face data. On shared devices, make the account-access implications explicit; unlocking the device can enable authentication.
- **Credential lifecycle:** show registered passkeys with human-meaningful labels, last-used/backup metadata when available, add/rename/revoke actions, and a warning before removing the last usable method. Server-side revocation does **not** automatically delete the passkey from the device's credential manager; a stale credential may still appear in autofill. Where supported, use WebAuthn signal APIs to reconcile server/client state, subject to authentication and privacy constraints.
- **Recovery is part of security:** loss of a device, provider account, security key or all passkeys must have a deliberate recovery route that is usable without a cognitive-memory test. A weak email/SMS recovery channel can undermine the phishing resistance of passkey sign-in; set verification, notifications, rate limits and re-enrollment rules from account risk rather than silently assuming every fallback is equivalent. Never claim that a passkey makes the *whole account* phishing-proof.
- **WCAG 2.2 SC 3.3.8 (AA):** every authentication step must avoid requiring unaided recall, transcription or puzzles unless one of the criterion's exceptions applies. Password managers, autofill and paste can be an assisting mechanism; passkeys are one alternative, not a requirement. Test OTP paste/autofill and conditional CAPTCHA paths, not just the initial login form. The stricter 3.3.9 is AAA. A biometric-only instruction is inaccurate because authenticators may use device PIN or other screen locks.
- **Implementation/security boundary:** verify server-issued challenge, RP ID/origin, signature, user verification flags when required, credential-to-account binding and replay protection **server-side**. Browser capability and `isConditionalMediationAvailable()` checks are progressive enhancement, not authorization. Browser+OS+credential-provider combinations differ; do not assume identical conditional autofill or cross-device behavior from browser name alone.

### Conditional Create: silent post-login upgrade is not conditional sign-in (reviewed 2026-10-25)

**Two different ceremonies:** `navigator.credentials.get({publicKey, mediation:"conditional"})` offers *existing* discoverable passkeys through form autofill and can remain pending. `navigator.credentials.create({publicKey, mediation:"conditional"})` is an *opportunistic registration* after a recent, successful, credential-manager-mediated sign-in (typically a saved password). It can create a passkey without a new modal when the browser/provider has prior user consent. Do not treat a passkey autofill capability check as an auto-enrollment capability check.

- **Gate on the actual flow, not a browser version.** `PublicKeyCredential.getClientCapabilities()?.conditionalCreate` is a client capability signal, **not** proof that the OS, chosen credential provider, saved-password history or user preference permits automatic creation. Chrome documented desktop support from 136 and Android from 142; passkeys.dev lists other platform combinations. Feature-detect, attempt only after the server has authenticated the *specific account*, and keep explicit, opt-in creation as a fallback. A `NotAllowedError` is not evidence that the user needs to be redirected to enrollment.
- **Consent and account control:** the Credential Management/WebAuthn drafts permit no new prominent modal only after earlier consent and recent mediated authentication. Chrome/Google Password Manager reports success and offers a Manage action/opt-out; that is **provider behavior**, not a promise about all clients. Keep a comprehensible passkey-management surface, allow removal and ordinary sign-in, explain shared-device implications, and do not automatically switch an account to passkey-only. Evaluate whether background enrollment fits sensitive or managed accounts before enabling it. Avoid stacking a misleading “all set” product toast on a provider notification before backend registration succeeds.
- **Server-side ceremony distinction:** verify the challenge, RP ID, origin, credential ID/algorithm, authenticated account binding and replay/duplicate protections before persisting. Conditional registration can legitimately return **UP=0**: skip the *user-presence* requirement **only for that conditional registration**, not for every WebAuthn ceremony. **UV is separate**: if registration policy requires user verification, verify UV=1; do not globally disable UV to make upgrades pass. In SimpleWebAuthn 14, `startRegistration({optionsJSON, useAutoRegister:true})` pairs with server `verifyRegistrationResponse({..., requireUserPresence:false})` for that response; the library's UV check is independent. W3C issue #2295 remains open, including a reporter's iOS 18.5 Safari/Passwords UV mismatch; treat it as a test case, **not** proof all current Safari versions fail.
- **Nonblocking upgrade and cleanup:** successful password login must remain successful if automatic creation fails or the provider refuses. A passkey can be created locally yet fail server verification/storage, leaving an orphan in autofill. Signal API hints (`signalUnknownCredential`, accepted-credential list, updated user details) may reduce stale entries, but providers need not act and the RP receives no reliable confirmation of cleanup. Offer a recovery/management path rather than promising remote deletion. Respect repeated declines and avoid forcing an extra setup screen after every auto-upgrade error.
- **Evidence, not universal uplift:** adidas reported a **47% passkey creation rate**, **8% more creations attributed to Conditional Create**, **>99% success among initiated passkey sign-ins**, and **<0.3% orphan-credential errors** after combined changes. This is a first-party production case study with mixed enrollment paths and additional Signal API/ROR work, **not** a randomized estimate of Conditional Create's causal UX improvement; its passkey-vs-historical-password success rates have different cohorts/denominators.

**Agent test contract:** test saved password with/without prior provider consent, missing provider support despite `conditionalCreate:true`, already registered credential, repeated decline, password-login success with `NotAllowedError`/`InvalidStateError`, UP=0 with UV-required/optional policies, client-created/server-rejected credential, stale autofill after revocation, shared-device account switching, Safari/iOS vs Chrome/Android, keyboard/screen reader and actual user comprehension. Measure *completed sign-ins, verified registrations, lockouts, surprises and recoveries*, not merely `create()` resolution.

Recovery strength and fallback risk are threat-model decisions, not blanket prohibitions. ## Onboarding: first successful task before a feature tour — 2026-10-21

**Decision:** treat onboarding as the shortest supported path to a user's *first meaningful outcome*, not a mandatory explanation of the interface. Start with an understandable primary action and contextual help; introduce a tour only when a genuinely unfamiliar interaction benefits from guided practice. Never infer activation from tour completion.

### Choose the learning mechanism by the task

- **Conventional, immediately usable workflow:** show the actual task, clear labels, a useful empty state and discoverable help. Avoid first-launch feature carousels or a compulsory tour that delays the user's goal. NN/g reports that out-of-context tutorials are often skipped or forgotten; this is a default, **not a ban**.
- **Novel spatial/gesture workflow:** offer an optional, replayable *hands-on* tutorial where users perform the action on a safe sample. Explain the result rather than listing controls. NN/g explicitly identifies novel paradigms as a possible exception; an 18-participant Paint 3D eye-tracking study also reports onboarding benefits, but cannot establish which pattern wins across products.
- **True prerequisites** (device pairing, security setup, required permissions, importing essential data): use a focused step-by-step task flow with honest progress, back/retry/help, preserved inputs and recovery after interruption. Do not offer a fake Skip when the service cannot function without the step; distinguish required setup from optional education. Device reconnection may need the same guidance as first setup.
- **Feature discovery after activation:** surface brief, dismissible cues at the point of use, with a persistent way to rediscover help. Microsoft Fluent explicitly recommends relevant, non-distracting, optional, benefit-focused teaching. Do not repeatedly resurface a dismissed cue merely because a user hasn't clicked the promoted feature.

### Implementation and accessibility contract

- Model `not-started → in-progress → completed`, plus `dismissed` for optional teaching, and `blocked/retry` for actual prerequisites. Persist meaningful task progress, not just which slides were seen; scope persistence to account/device as appropriate. Allow users to restart optional guidance and continue work without it.
- Anchor a cue to a stable, visible target; when responsive layout, permissions or personalization remove the target, omit or relocate the cue rather than pointing into empty space. Don't cover the very control being taught or hijack scrolling to follow it.
- A spotlight with actions is **not** a tooltip. Use appropriate dialog/popover semantics and test Escape, initial focus, Tab order, return focus, zoom, touch, screen-reader announcements and small viewports. If modal, follow the WAI-ARIA APG modal focus contract; do not use a modal solely to force reading promotional copy.
- Atlassian's current Spotlight guidance favors one step, at most three for its tours, and a first-focusable dismiss control; this is a **component-specific heuristic**, not a universal cognitive limit. Its older `@atlaskit/onboarding` package is deprecated in favor of `@atlaskit/spotlight`; current `@atlaskit/spotlight` uses subpath imports, so verify version/API rather than copying legacy examples.
- **Falsification:** compare no tour, contextual help and optional hands-on guidance using first-task completion/time, error/recovery, later feature use, help rediscovery, and interruption cost; include returning users, keyboard/AT, mobile, slow loading, target removal and clean controls. Vendor design-system rules are implementation guidance, not causal evidence that a tour increases retention.

**Evidence:** [NN/g tutorial vs contextual help (2023)](https://www.nngroup.com/articles/onboarding-tutorials/); [NN/g smart-device setup (2025)](https://www.nngroup.com/articles/smart-device-onboarding/); [Microsoft Fluent onboarding](https://fluent2.microsoft.design/onboarding/); [Atlassian Spotlight](https://atlassian.design/components/spotlight/code) and [changelog](https://atlassian.design/components/spotlight/changelog); [WAI-ARIA APG modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/); [Megyeri & Szabó, Paint 3D study (2021, n=18)](https://doi.org/10.1177/10648046211026028). No cross-product controlled outcome study was established in this cycle.

## Date entry: choose by user task, not picker fashion — 2026-10-20

**Decision:** ask what the date *means* before choosing a control or storage type. A known birthday, a date copied from a document, an approximate month, a booking date, and a time-zone-specific appointment are different tasks. A calendar is not automatically more usable than typed fields.

- **Known or document dates:** prefer directly editable, clearly labelled day/month/year fields (GOV.UK) or a month select with day/year text fields (USWDS). Both are defensible production patterns; neither is a universal winner. Match the order/format printed on a document when copying it. Group fields with `fieldset`/`legend`; label each part and give an unambiguous example. Use `type="text" inputmode="numeric"` for numeric day/year rather than number spinners; do not auto-advance focus. GOV.UK accepts full/abbreviated month names based on observed errors; USWDS uses a month select. Treat this as a local design decision, not a contradiction to erase.
- **Approximate or relative dates:** if users only know “March 2024,” do not silently manufacture March 1 as a precise date. Represent precision explicitly and validate the question's actual requirement. If users think “tomorrow” or “three days before,” resolve it against a clearly stated reference date and relevant time zone, and show the resulting calendar date before committing.
- **Scheduling/weekday context:** a calendar can help users compare nearby dates and availability. Keep a direct-entry route; both GOV.UK and USWDS warn against calendar-only input. Native `<input type="date">` is a reasonable low-complexity candidate when its platform-specific UI, typing affordance, locale presentation, min/max constraints and mobile accessibility work for the actual audience. Its `value` is normalized `YYYY-MM-DD`, independent of displayed locale. A bespoke calendar incurs month navigation, focus, grid keyboard controls, screen-reader announcements, unavailable-date explanation, touch, localization and testing obligations. W3C APG date-picker examples are **illustrative, not production-ready**.
- **Validation and recovery:** distinguish missing parts, impossible dates (e.g. 31 February), out-of-policy ranges, unavailable appointments and server-side booking conflicts. Preserve the user's entries and explain the precise fix; validate on the server too. A date being syntactically valid does not make a booking available. Do not auto-submit on calendar selection. In a date range, explain start/end constraints without silently swapping dates.
- **Date-only is not an instant:** store a birthday or all-day calendar date as a civil date (for example, ISO `YYYY-MM-DD`), not as UTC midnight later formatted in an arbitrary locale. JavaScript `new Date("2026-10-20")` parses date-only ISO as UTC; `input.valueAsDate` must be read with UTC getters or it can appear as the previous day west of UTC. Avoid converting through `Date` when a date-only string or a verified `PlainDate`-style type suffices.
- **Appointments need zone policy:** `datetime-local` contains no time-zone identifier and may accept nonexistent local wall times during a daylight-saving gap; repeated fall-back times can refer to two instants. Ask which location's zone governs the event, preserve an IANA zone identifier when relevant, and define how the system resolves ambiguous/nonexistent times. Only convert to a UTC instant after applying that policy; do not assume the user's current device zone is the venue's zone. Temporal's `PlainDate`/`ZonedDateTime` distinction is a useful model, but verify runtime support or use a reviewed library.

**Agent acceptance checks:** known vs approximate vs scheduling tasks; typed entry and calendar route; keyboard/screen reader/touch; 320px/zoom; locale day-month ordering; leap years and impossible dates; timezone west/east of UTC; DST gap/overlap; stale availability; server rejection; clear focus and error recovery. Compare task success and correction cost before claiming a picker is superior. USWDS reports manual-entry trouble in its own date picker despite an accessibility test status; component test passes do not settle usability.

**Evidence:** [GOV.UK dates](https://design-system.service.gov.uk/patterns/dates/), [GOV.UK date input](https://design-system.service.gov.uk/components/date-input/), [USWDS memorable date](https://designsystem.digital.gov/components/memorable-date/), [USWDS date picker](https://designsystem.digital.gov/components/date-picker/), [MDN date input](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/date), [MDN valueAsDate](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/valueAsDate), [MDN Date parsing](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Date), [MDN datetime-local](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/datetime-local), [Temporal time zones](https://tc39.es/proposal-temporal/docs/timezone.html), [W3C APG date picker](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/). ## Recurring appointments: local-clock intent, DST and instance identity — 2026-10-24

**Decision:** a recurrence is not a list of UTC timestamps. Distinguish (a) a one-off exact instant, (b) a **local-clock series** (every Tuesday 09:00 in Madrid), (c) fixed elapsed intervals (every 168 hours), and (d) floating reminders (09:00 wherever the user is). These diverge when the participant travels or the zone's offset changes. Do not convert a weekly local-clock series to repeated 604,800-second additions.

**Data and duration contract:** for a location-anchored series, retain the local start date/time, IANA zone ID, recurrence rule, duration semantics, series ID and original occurrence IDs. Derive UTC instants for individual occurrences with reviewed time-zone rules. RFC 5545 distinguishes recurring `DTEND` (same **exact** duration) from `DURATION` (same **nominal** duration, which can span 23/25 elapsed hours across DST). Future time-zone legislation may invalidate precomputed UTC instants; preserve local intent and re-evaluate future dates when zone rules change.

**Critical standard/library contradiction:** RFC 5545 §3.3.10 says recurrence instances on nonexistent local times must be **ignored and not counted**, but later in the **same section** says such instances are interpreted as explicit DATE-TIME values under §3.3.5. That latter rule shifts a skipped time using the pre-gap offset and selects the first of two repeated times. Do **not** assert a universal skip/shift rule from the RFC. Temporal's `compatible` mode shifts forward at gaps and chooses the earlier overlap; `reject` allows explicit product handling. In a local Python test, `dateutil` **2.9.0.post0** expanded a daily `Europe/Madrid` 02:30 series to include the **nonexistent** `2026-03-29 02:30 +02:00`, despite its documentation saying invalid recurrence times are ignored; its monthly Jan-31 example *did* skip nonexistent dates. This is a version-specific falsification, not evidence of every engine's behavior.

**Exception/edit contract:** a moved occurrence must retain its original logical identity. Google Calendar's immutable `originalStartTime` identifies the occurrence even when `start` changes. Store overrides/cancellations against that original key, not just the current timestamp. Offer explicit **this occurrence / this and following / entire series** scope. Google warns against editing all future instances individually because it creates many exceptions and notifications; its documented “this and following” operation splits the series. Check permissions, attendees and notification consequences before commit.

**UX and acceptance:** show the event zone, local clock time, rule and a preview of several actual occurrences before saving; label attendee-local conversions. Explain the product's skip/shift/earlier/later policy at DST gaps/overlaps rather than silently changing a consequential appointment. Preview edit scope and preserve failed edits. Test weekly 09:00 across both DST changes; `2026-03-29 02:30` (Madrid gap); `2026-10-25 02:30` (two instants); Jan-31 monthly `COUNT`; duration across a transition; moved/canceled instance; series split; participant zones; changed zone data; stale availability and rollback. Compare provider/library round-trip to the preview. A date-picker passing accessibility checks does not prove recurrence correctness.

**Evidence boundary:** RFC 5545, Temporal and Google are primary protocol/API evidence; the dateutil probe is a local version-specific observation. Preview/confirmation advice is agent synthesis, not a measured UX or cross-library interoperability result.

## Search, filtering, and result-set orientation

Treat search, filters, sort, result count, applied state, and result navigation as one **result-set control system**. The user should always be able to answer: what did I ask for, what constraints are active, what set am I viewing, and how do I broaden or narrow it?

### Separate retrieval from refinement
Use search when the user can express a target or identifying clue; use filters to refine a known result set. Avoid turning “advanced search” into a dense form when progressive refinement will do. For exact-identifier workflows, surface the matching record rather than silently navigating into it so the user can verify the match.

### Make applied state visible outside the controls
Do not rely on checked boxes inside a sidebar/drawer as the only record of state. Show a compact applied-filter overview near the results, especially when controls can be hidden or off-screen. Each applied constraint should be removable; provide “clear all” when several constraints can accumulate. A bare badge such as “3 filters” is weaker than naming the active constraints.

### Apply timing is a product decision, not a universal rule
Use explicit apply when users commonly choose several criteria, updates are expensive/slow, result movement destabilizes controls, or a predictable submit-result transition matters. Live filtering can fit fast stable updates where each selection is independently meaningful and immediate feedback helps. If updates are dynamic, announce concise result status without stealing focus.

### Preserve orientation after a result-set change
After search/filter/sort, show query and constraints, show a useful result count, apply controls to the whole set, reset pagination when the set changes, avoid unnecessary focus jumps, and expose in-place result/status changes programmatically.

### Zero results are a recovery state
Preserve query and constraints, state that no matches were found, and provide the cheapest relevant recovery actions. Do not silently substitute unrelated results without labeling that change.

### Mobile filters
Keep the filter entry point tied to results, surface applied state outside hidden panels, and make return to updated results obvious.

### Pagination vs continuous loading
- **Pagination** favors location, returnability, explicit progress, deep linking, and bounded loading.
- **Load more** can preserve browsing continuity while retaining an explicit user action.
- **Infinite scroll** fits low-commitment feeds better than goal-directed retrieval; avoid it when users need stable position, comparison, keyboard navigation, footer access, or reliable return.

### Implementation checks
Test query persistence, back/forward, deep links, refresh, empty/error states, race conditions, focus, announcements, keyboard filtering, zoom/reflow, mobile drawers, result-count accuracy, sort/filter interaction, pagination reset, and return-from-detail restoration.

## Search/filter evidence boundary
Baymard supplies behavioral evidence for ecommerce product lists. GOV.UK/MOJ/DWP/Home Office provide deployed public-service guidance. W3C defines dynamic status-message requirements. Live vs explicit apply remains conditional on task, latency, stability, and tested accessibility.

## Bulk selection across filters and pages: scope is part of the action — 2026-10-12

**Decision rule:** a checked row is an item; a checked page is a page; “all matching results” is a *query*. Never let the same unlabeled “Select all” control silently switch among those meanings. For small datasets, explicit IDs suffice; for large server-filtered sets, selecting a query needs a separate, visible escalation step.

### Selection model and transitions
- **Explicit selection:** `{mode: "ids", ids: Set<stableResourceId>}`. Page-header select/deselect adds/removes *only eligible IDs on the current page*, preserving selections on other pages if cross-page selection is promised. Calculate header checked/mixed/unchecked from eligible page IDs, with an explicit empty-page guard. Do not use row indices as identifiers.
- **Query-wide selection:** `{mode: "matching", filterSnapshot, excludedIds, scopeVersion?}`. After “All 50 on this page selected,” offer “Select all 2,430 matching items” only when the backend can actually execute that scope. This is **not** a client-side set of 2,430 IDs. Bind the operation to the confirmed query, exclusion set, resource type/tenant, and an explicit *snapshot-versus-live-membership* policy.
- **Scope changes:** changing search/filter or switching resource set must either clear query-wide selection with explanation or require deliberate reconfirmation. Sort-only changes normally alter order rather than membership; do not reset selection reflexively unless the product's scope contract changes. If explicit IDs survive filtering, show the total selected *including hidden rows* and offer clear selection; do not imply the visible checkboxes are the full set.
- **Counts and eligibility:** derive “N selected” and actionable count from the authoritative selection scope, not from the current page length. Disable or explain ineligible rows; the server must recheck per-item permissions and current eligibility at execution time. If totals are approximate or changed since selection, say so before a consequential action.

### Action and recovery contract
Use specific verbs and resource names (“Archive 50 products,” not “Apply”). Before destructive or hard-to-reverse actions, confirm the *scope*, filters, count, and consequences. The backend must validate the operation and each target against current authorization; never treat disabled checkboxes or client-supplied filters as a security boundary. Decide whether matching-set execution uses a fixed snapshot or the set at execution time; prevent unintended expansion if new matching records appear after confirmation. For long jobs, show queued/running/completed/partial-failure states, idempotent retry where supported, and a result summary (succeeded, skipped, failed). Preserve failed-item selection and recovery controls; clear only the successfully completed portion or after an explicit reset.

### Accessibility and implementation pitfalls
Use native labelled checkboxes when possible; name the header control with its actual scope (“Select all 50 items on this page”). The mixed state is **not** a third submitted boolean: `input.indeterminate` is presentation-only and must be synchronized from actual selection state. Ensure keyboard access to rows, bulk toolbar, confirmation and recovery; announce meaningful selection/result changes without flooding live regions. A custom `role=checkbox` needs its own keyboard/state behavior; APG examples are illustrative, not tested production widgets.

**Library trap (verified 2026-10-12):** Shopify's *page-only* migration snippet uses `setSelectedIds(checked ? new Set(pageIds) : new Set())`; copying that handler into a cross-page UI silently discards off-page IDs. Its separate migration guidance correctly requires an explicit page-to-query escalation. TanStack Table documents that with `manualPagination`, `getSelectedRowModel()` contains only loaded-page rows even when row-selection state holds off-page IDs. MUI X supports include/exclude selection models and `keepNonExistentRowsSelected` but warns that select-all and server pagination can leave unexpected retained selections; component state is not the authoritative backend operation contract. Audit exact installed library/version and adapt behavior rather than assuming a built-in checkbox solves cross-page semantics.

**Release tests:** page A select → page B select → deselect page B → return A; sort and filter changes; hidden selected items; empty page; select-all then exclude two; changing counts/data/permissions between preview and execute; another user editing/deleting targets; huge result sets; partial success and retry; mobile, keyboard, screen reader, zoom, and destructive confirmation. Test *actual affected IDs* and recovery, not merely visual checkbox states.

**Evidence boundary:** Shopify's current migration docs establish a shipped product pattern and expose a copy/paste pitfall; TanStack/MUI document framework state semantics; W3C/MDN document checkbox mechanics; OWASP establishes server-side authorization. The snapshot/live-set and partial-failure rules are risk-based agent synthesis, not controlled UX outcome evidence. No study here proves bulk selection improves speed for every task.

## Optimistic edits: distinguish provisional UI from saved state — 2026-10-13

A quick visual response is not a confirmed write. For low-risk predictable changes, provisional rendering can improve responsiveness; for consequential actions or complex server validation, prefer visible pending state until confirmation. Distinguish local draft, durable offline queue, sending, server-confirmed, and needs-attention states. Do not label a locally queued change “Synced.”

React's `useOptimistic` supplies temporary rendering, not persistence. TanStack Query offers pending-variable rendering as a simpler alternative to shared-cache mutation; concurrent mutations and refetches can make naive rollback display stale data. Server-side version checks (`If-Match` / HTTP 412) protect against lost updates; optimistic rendering alone does not. Browser `navigator.onLine` is unreliable, and Background Sync is not universal. Preserve edits after rejection, provide recovery, and test concurrent updates, timeout-after-commit, offline restart, and accessible status announcements.

## Offline edits and synchronization: local durability is not server acceptance — 2026-10-24

**Decision:** support offline mutation queues only for operations that can be safely replayed, reconciled, and explained. An optimistic screen, a persisted local draft, a queued request, and a server-accepted change are **different promises**. Do not show an unconditional “Saved” checkmark for a write not acknowledged by the authoritative service. Payments, irreversible deletion, time-sensitive approvals, and actions requiring fresh authorization usually need explicit online confirmation rather than automatic replay.

### A truthful per-item state contract

| State | What the UI may claim | Failure boundary |
|---|---|---|
| Editing | “Editing” | Do not claim durability until the local storage transaction succeeds. |
| Stored locally | “Saved on this device; not synced” | Browser/device reset, private-mode exit or eviction can still remove it. |
| Queued | “2 changes waiting to send” | Show pending state on affected items, not just a global banner. |
| Sending / uncertain | “Checking whether changes reached the server” | A timeout does **not** prove failure; do not mint a second logical operation. |
| Server confirmed | “Synced” and relevant last-success time | Only after authoritative acknowledgement or reconciliation lookup. |
| Rejected / conflict / expired | “Needs attention” with specific reason | Preserve local edit and offer compare, retry, export or manual resolution. |

Use a quiet contextual status while important work remains pending; an ephemeral toast is insufficient. Distinguish inbound data freshness from outbound unsent changes. Announce meaningful transitions through accessible status semantics, not every retry. Manual “Sync now” should not promise immediate delivery. Google's Open Health Stack guidance supports contextual status, last-sync timestamps and recovery for healthcare workflows; it is not a controlled universal usability result.

### Correctness is an application contract, not a service-worker feature

1. **Persist before promising.** Store a versioned operation record with logical operation ID, account scope, resource, expected server version, dependencies, payload, creation/expiry time and stable idempotency key where supported. Handle quota errors and migrations. IndexedDB is best-effort by default; StorageManager.persist() reduces eviction risk but cannot prevent deliberate deletion or device loss.
2. **Choose replay by consequence.** Independent low-risk draft updates can retry; create-then-edit needs dependency ordering. Do not auto-replay stale destructive operations. Reauthenticate and reauthorize every replay on the server; quarantine/clear pending operations on sign-out or account switch. Never persist bearer tokens in a generic queue, and minimize sensitive queued payloads.
3. **Deduplicate and reconcile.** A response can be lost after server commit. Reuse the same idempotency key and unchanged payload only within the endpoint's documented retention window; after expiry, query operation status before replay. Stripe's current documentation distinguishes API v1 (first response cached **including HTTP 500**, key retention at least 24h) from API v2 (different partial-failure semantics); neither is a universal API guarantee. For concurrent edits, server version/ETag preconditions (If-Match; usually HTTP 412 on mismatch) protect against silent overwrites, but require a visible compare/recovery flow.
4. **Treat connectivity as a hint.** navigator.onLine is unreliable. Background Sync is not Baseline; scheduling is browser-managed and may be delayed. Workbox fallback on browsers without Background Sync replays when the service worker starts, **not reliably while the app is closed**. Provide foreground retry on reopening and manual recovery.
5. **Workbox source-level trap (inspected 2026-10-24).** BackgroundSyncPlugin enqueues thrown fetchDidFail exceptions, **not HTTP 4xx/5xx by default**. More subtly, Queue.replayRequests() awaits fetch(entry.request.clone()) but never checks response.ok: a queued replay returning HTTP 503 is **removed as though successful**. A fetchDidSucceed status-throwing plugin on the initial route does not change this replay loop. If HTTP failures must remain queued, implement and test a reviewed custom onSync/replay policy with explicit response validation; do not blindly retry authorization, validation or conflict responses.
6. **Manual replay concurrency and dependent-write loss (source-extracted test, 2026-10-24).** `Queue.replayRequests()` has no single-flight guard: it removes an entry *before* awaiting its fetch. Two overlapping manual calls can therefore send B before A has completed. Executing the exact Workbox **v7.4.1** replay method in isolation with mocked queue/fetch produced `create-start → edit-404 → create-201`; both entries disappeared, but the dependent edit never applied. A separate 503 replay emptied the queue, whereas a rejected fetch requeued its entry. This proves the method-level failure path, **not** real-browser scheduling or a production Workbox installation. Do not call `replayRequests()` from overlapping timers, multiple UI messages, or other concurrent entry points; avoid reaching into `BackgroundSyncPlugin._queue` (private). Use one controlled replay owner, explicit dependency ordering and status-aware `onSync`/recovery where needed, with server-side idempotency, authorization and version preconditions. An in-memory mutex cannot guarantee ordering across service-worker termination or multiple devices. A historical ordering report (#2640) was closed during the 2024 issue-backlog reset, **not** demonstrably fixed.
7. **TanStack Query v5 boundary.** Persisted mutations restore state, not executable functions. Register a matching default mutation function before resumePausedMutations() after reload or replay may fail with “No mutationFn found.” Mutations run in parallel by default; shared scope.id serializes only matching operations. The mutation cache alone does not implement server deduplication, conflict resolution or account isolation.

**Agent falsification fixture:** offline create/edit → refresh → reconnect; drop response *after* server commit; return 503 on first send **and again on Workbox replay**; return 401 after sign-out, 412 after another device edits, and 422 for invalid input; run two overlapping manual replays while a create request is held in flight and its dependent edit returns 404; exhaust quota, evict storage, change app schema, close Safari, and switch accounts with pending work. Verify actual server writes/no duplicates, queue retention, truthful UI, preserved edits, accessible status/focus, expiry and recovery. Include an online-only control for high-risk actions. **The pinned Workbox replay method was executed in an isolated mocked harness; no full Workbox/IndexedDB/service-worker, cross-browser or user benchmark was performed.**

## Loading, progress, empty, and error states

Treat asynchronous UI as a **state machine**, not a spinner decoration. Define idle, pending, success-with-data, success-with-no-data, and failure; add stale/refreshing, partial, queued, or cancelled states when real.

### Preserve useful context while work is pending
Keep already-valid content visible during background refreshes where possible. Scope blocking and loading feedback to what is actually unavailable.

### Choose the indicator from what the system knows
- **Skeleton:** when destination structure is predictable and reserving geometry reduces reflow.
- **Spinner / indeterminate activity:** for bounded work whose meaningful progress cannot be estimated.
- **Determinate progress:** when trustworthy quantitative progress exists; never fabricate percentages or ETA.
- **Inline pending state:** for mutations, adjacent to the initiating action or affected object where possible.

### Prevent loading UI from causing layout instability
Reserve approximately final geometry. Performance engineering should remove latency where possible rather than only mask it.

### Make completion and failure unambiguous
Preserve valid information, state failures in task language, distinguish failure classes when remedies differ, keep recovery near the failed region, and never present stale data as freshly confirmed.

### Empty is not the same as error
Empty means the system successfully has no content; error means intended state could not be obtained or changed.

### Accessibility contract
WCAG 4.1.3 covers status messages for waiting, progress, results, or errors without moving focus. Use appropriate semantics and avoid chatty announcements. Native `<progress>` is preferable when it fits.

### Implementation checks
Test fast/slow responses, offline/network failure, retry, partial/stale data, background refresh, duplicate submission, cancellation, navigation, focus, screen readers, reduced motion, geometry, and unrelated controls.

## Loading-state evidence boundary
W3C defines accessibility behavior. Carbon and Atlassian provide mature production guidance separating skeleton, loading, and progress use cases. These sources do not establish a universal wait threshold or prove skeletons always feel faster.

## Notifications and toasts: choose persistence before presentation

Treat a notification as **information with a consequence and an expiration policy**, not a generic floating component. Choose the surface from the user's next required action and whether the message can be recovered.

### Surface and dismissal contract

- **Transient, non-critical confirmation** (for example, a save also reflected in the document): a short non-modal toast/status may auto-dismiss **if the same information remains discoverable elsewhere**. Do not make it the sole proof of success.
- **Field/task failure:** use a persistent message adjacent to the affected object, with field-level recovery and an error summary when appropriate; a toast alone is insufficient.
- **Important system-wide condition:** use a persistent banner/notification center entry that remains findable after navigating. Avoid burying outages or unsaved changes in a disappearing corner.
- **Action required, including Undo:** keep the action available until explicitly resolved/dismissed or provide an equally usable persistent recovery route. Do not make a five-second toast the only way to reverse a consequential operation.
- **Decision that must interrupt work:** use a properly managed dialog/alert dialog, not an assertive toast that pretends to be modal.

**Timing nuance:** WCAG 2.2 SC 2.2.1 (Level A) explicitly allows a five-second email-arrival toast when the inbox offers another way to discover the same information; if the toast is the **only** way to obtain the information or perform an action, the time limit must satisfy that criterion. This is not a blanket five-second accessibility rule. WAI-ARIA APG separately cautions against automatically disappearing **alerts**; the two recommendations address different consequences. A minimum duration alone does not make a toast accessible.

### Announcements and focus

- For routine completion/progress use a concise `role="status"` (polite). Reserve `role="alert"` (assertive) for urgent, time-sensitive text; frequent alerts interrupt screen-reader work. WCAG 4.1.3 (Level AA) requires status messages to be programmatically determinable without stealing focus.
- Neither `status` nor `alert` is a substitute for a keyboard-operable interactive component. Do not put buttons inside the **alert text** region and assume the announcement exposes their function. If an actionable notification is used, provide a separately reachable control and explicit focus/return behavior; if a response must interrupt, use an alert dialog.
- Establish live regions before updating their text where practical; newly mounted populated regions and repeated identical strings may not announce consistently. Test the actual browser/screen-reader combination rather than assuming DOM or axe checks prove an announcement occurred.
- A persistent actionable toast must be discoverable from the keyboard without requiring pointer hover. React Aria's toast region supports F6 navigation and restores focus; that is a **library implementation**, not a universal native browser shortcut.

### `ariaNotify()` (2026): method availability is not an audible status guarantee

**Decision:** keep visible, persistent task state and a tested status-announcement path; do **not** replace live regions across an entire product merely because `document.ariaNotify` exists. MDN marks `Document/Element.ariaNotify()` **Baseline Newly Available since September 2026**, not universally deployed to older browsers or proven audible with every screen reader. Calls return `undefined`; a supported method, successful call, or passing DOM/axe assertion **cannot prove speech or braille delivery**. A blocked `aria-notify` Permissions Policy also fails **silently**, so `typeof document.ariaNotify === "function"` is not a sufficient fallback gate. For critical save/error/progress feedback, retain a tested live-region route and visible state; where adopting `ariaNotify`, use **one** announcement channel per verified environment rather than unconditionally speaking through both.

**Queue, priority and context:** coalesce related updates into one short, localized message; rapid calls may replace one another and `aria-live` can take precedence. Use normal priority for routine results, high only for truly urgent interruptions; do not announce every upload tick or every streaming token. `Element.ariaNotify()` can be ignored if its target is excluded from the accessibility tree; select a stable exposed element with appropriate `lang` ancestry for multilingual announcements. `Document.ariaNotify()` uses document language. The current API has no per-call `lang`/`dir` option. An announced string is not a keyboard-operable Undo button, durable error message, or focus-management mechanism.

**Cross-origin security/documentation contradiction (checked 2026-10-25):** the [WAI-ARIA 1.3 editor's draft dated 2026-10-21](https://w3c.github.io/aria/#arianotify-permissions-policy) and its June Working Draft specify default `aria-notify` allowlist **`*`**, permitting cross-origin frames without explicit delegation; [MDN's Permissions-Policy page](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Permissions-Policy/aria-notify) still says **`self`** (last edited March 7). Do not silently choose MDN's more restrictive claim as a security guarantee. [W3C security review #2861](https://github.com/w3c/aria/issues/2861) remains open and explicitly raises announcement flooding from embedded content; this is a *threat model*, not a reproduced exploit. If embedding untrusted origins, decide whether to set `Permissions-Policy: aria-notify=(self)` (or `aria-notify=()` if no document should use it), and test that legitimate third-party accessible status messages still have a usable path. The permissive default is a deliberate accessibility-versus-disruption trade-off, not proof that all browsers enforce it identically.

**Acceptance test:** same save/error/undo journey with live region, `ariaNotify`, and no API; Chromium/Firefox/Safari + NVDA/JAWS/VoiceOver/TalkBack where available; older versions, rapid repeats, hidden/excluded target, locale changes, interrupted speech, high/normal priority, policy-disabled frames, same-/cross-origin embeds, and zero duplicate or missing *essential* announcements. A June 2026 [practitioner matrix](https://oidaisdes.org/de/blog/aria-notify-browser-support/) observed success on tested Windows/Android combinations and failure on **Safari 26.5/iOS 26.5**, which **does not establish failure in Safari 27**. The local Chromium 144 probe confirmed the API is exposed and its feature policy reports allowed in a blank document; browser navigation to a local cross-origin fixture was blocked by the test environment, and no screen reader was exercised. **Evidence boundary:** standards/documentation contradiction plus platform/practitioner reports, not cross-origin runtime or assistive-technology certification.

### Implementation and failure checks

Specify a single owner for queueing, deduplication, priority, replacement and dismissal; otherwise repeated saves/background jobs can stack overlays and flood live announcements. Avoid obscuring essential controls at narrow widths, 200–400% zoom, mobile keyboards and safe-area insets. Pause any *permitted* auto-dismiss timer on hover/focus (and consider inactive tabs), but **do not use pause as a substitute for persistence** when a unique action or important information is at stake. Verify screen-reader announcement, keyboard reachability and focus restoration, action expiry, repeated identical messages, concurrent errors, offline/retry, navigation, and reduced motion.

**Evidence boundary (reviewed 2026-10-09):** [WCAG 2.2.1](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable) supplies the explicit alternative-access exception; [WCAG 4.1.3](https://www.w3.org/WAI/WCAG21/Understanding/status-messages) defines status semantics; [WAI-ARIA APG alert](https://www.w3.org/WAI/ARIA/apg/patterns/alert/) and [MDN live regions](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Guides/Live_regions) explain interruption/announcement pitfalls. Current [Carbon notification patterns](https://www.carbondesignsystem.com/building-blocks/core/patterns/notifications) distinguish persistent actionable toasts from optional timed informational toasts; [React Aria Toast](https://react-aria.adobe.com/Toast) supplies one implemented keyboard/timer model. Carbon's older v10 guidance warns against interactive toasts while its current guidance supports **persistent** actionable notifications: do not treat historical component limitations as a universal prohibition. These are standards/platform and production-design-system mechanisms, not controlled evidence that toasts improve outcomes.

## Web push permission: grant is not subscription — 2026-10-13

**Decision:** ask for system notification permission only when the user has opted into a concrete, valuable alert (delivery update, followed topic, price change). Never request it on page load or treat an OS-level grant as consent to every notification category. Provide a persistent in-product preference/opt-out route; keep essential task information available inside the app even when push is unavailable.

**Separate the states:** (1) feature preference in the user's account, (2) browser/OS permission (`default`, `granted`, `denied`), (3) device-specific Push API subscription, (4) server-side endpoint/account association, and (5) actual delivery. None proves the next. A granted permission does not create a push subscription, and a successful subscription does not prove delivery. Reconcile these states on activation, resume and settings changes; don't display “alerts enabled” until the required server registration succeeds. Guard subscription and server writes against duplicate concurrent calls; remove stale endpoints and honor account switching/sign-out.

**2026 browser change:** Chrome 155 on Android introduces a non-blocking notification prompt. If it times out, `Notification.requestPermission()` resolves `default`; users can subsequently grant permission through Chrome's site controls **without repeating the original request**. Code that subscribes only inside `requestPermission().then(permission => permission === 'granted')` can therefore miss the later grant. Where supported, observe `navigator.permissions.query({name: 'notifications'})` / `PermissionStatus.onchange`, *and* reconcile the current state immediately and on return to the app; treat the change event as a trigger to check, not as proof of an existing subscription. This is a **Chrome Android 155 behavior**, not a universal browser promise.

**Platform boundaries:** Push needs HTTPS, a service worker, an actual PushSubscription (typically `userVisibleOnly: true` and a VAPID public key), and a functioning push backend. On iOS/iPadOS, WebKit supports Web Push for eligible **Home Screen web apps**, not an ordinary Safari tab; permission must follow direct user interaction. Feature-detect, explain the install prerequisite only when relevant, and offer in-app/email alternatives. Browser controls can revoke permission independently: Chrome's 2025 policy targets high-volume, low-engagement sites, while excluding installed web apps. Never repeatedly nag after denial or assume a previous grant is permanent.

**Validation:** no permission, ignored/timed-out prompt, later grant in browser controls, explicit denial, permission revocation, offline/expired endpoint, duplicated subscribe calls, account change, multi-device settings, quiet hours, sensitive lock-screen previews, iOS Safari tab vs installed app, keyboard/screen-reader operation. Evaluate useful delivery and opt-out rates, not just permission-grant conversion.

**Evidence boundary:** Chrome documents the new prompt and its `onchange` consequence; WebKit and MDN document platform mechanics; Google's engagement and revocation data are vendor-reported, not a controlled demonstration that push improves product outcomes. Sources: [Chrome 155 Android prompt (2026-07-22)](https://developer.chrome.com/blog/notification-prompts-android), [Chrome notification revocation (2025-10-10)](https://blog.google/chromium/automatic-notification-permission/), [WebKit iOS Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [MDN permission](https://developer.mozilla.org/en-US/docs/Web/API/Notification/requestPermission_static), [MDN PushManager.subscribe](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe).

## Async comboboxes: preserve typed text and committed selection — 2026-10-10

**Choose the interaction before choosing ARIA.** A native `<select>` is usually the lower-risk choice for a manageable, stable set; a combobox earns its complexity when users need search/filtering over a large or changing set. If arbitrary text is valid, define that explicitly; if only catalog items are valid, show a clear validation/recovery path. For multiple choices, consider a filterable list with persistent checkboxes before adopting token/chip-based multi-select. React Aria now supports multi-select ComboBox, but library support alone does not establish usability for a particular task.

**Model three different states:** (1) `inputText` — what the user typed, (2) `activeOptionId` — the suggestion currently navigated/highlighted, and (3) `committedValueId` (or IDs) — the actual form value. Merely highlighting a suggestion must not silently commit it. Decide whether blur restores the committed label, preserves free text, or displays an explicit unresolved-value error; React Aria's current ComboBox defaults to restoring the selected item on blur unless `allowsCustomValue` is enabled. Keep the distinction visible to users and to submission logic.

**Keyboard and assistive-technology contract:** WAI-ARIA APG documents editable combobox variants with manual versus automatic suggestion selection; neither is a universal default. For listbox popups, keep DOM focus on the text input while `aria-activedescendant` tracks the active option; connect the visible popup with `aria-controls`, reflect open state with `aria-expanded`, and use `aria-autocomplete` according to actual behavior. Preserve native text-editing keys; `Escape` dismisses suggestions, while `Enter` accepts an actively navigated option. Do not hijack `Enter` while an IME composition is active. A popup containing buttons or a complex editor is not automatically a listbox; use the correct dialog/grid interaction model or simplify it. APG examples are illustrative, not production certification.

**Async contract:** debounce only when justified by backend cost/latency; it does not prevent races. Cancel obsolete requests where possible *and* guard against stale completions (request generation/query identity) before changing visible results. React's own docs demonstrate why older searches can resolve after newer ones; React Aria `useAsyncList` supports abortable loads and explicit loading/error state. Do not replace results for the current query with late results for a previous query. Distinguish “no matches” from “request failed” and offer retry. If the active option disappears after filtering, clear/reconcile `aria-activedescendant` rather than referencing a removed DOM node. Keep previously committed selections stable when suggestion pages change.

**Input modality and fallback:** IME `compositionstart`/`compositionend` delimit in-progress character composition; defer commit/navigation shortcuts during composition and test the event order in supported browsers. Verify touch exploration, dictation/voice control, screen magnification, mobile virtual keyboards, zoom, and screen readers rather than treating axe/ARIA validity as sufficient. GOV.UK's accessible-autocomplete is a useful implementation study, but its own README says maintenance is minimal and lists incomplete testing for newer React/Preact versions; do not treat its name as a blanket accessibility guarantee. Where feasible, progressively enhance a server-rendered native control so the form still works without the custom widget.

**Release checks:** rapid typing with out-of-order responses; query deletion and empty query; zero results, timeout and retry; composition with Enter; pointer/touch selection; blur and Escape; keyboard cursor editing; selected value no longer in the loaded page; focus/announcements after async updates; zoom/voice input; and native fallback. Compare task completion and correction errors, not just ARIA attributes.

**Evidence boundary:** APG establishes interaction patterns; React Aria and React document concrete implementation behavior; MDN documents composition events; GOV.UK documents operational maintenance constraints. These sources do not prove that autocomplete is faster or more accessible than native select/checkbox alternatives for all audiences. Sources: [WAI-ARIA APG combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), [React Aria ComboBox](https://react-aria.adobe.com/ComboBox), [React Aria useAsyncList](https://react-aria.adobe.com/useAsyncList), [React race-condition guidance](https://react.dev/learn/you-might-not-need-an-effect), [MDN compositionend](https://developer.mozilla.org/en-US/docs/Web/API/Element/compositionend_event), [GOV.UK accessible-autocomplete](https://github.com/alphagov/accessible-autocomplete), [GOV.UK checkbox guidance](https://design-system.service.gov.uk/components/checkboxes/).

## Comparison interfaces: preserve decision context — 2026-10-23

**Decision:** comparisons should let users verify a *specific decision*, not merely find the most visually distinct cell. Use a side-by-side matrix for a manageable number of alternatives when attributes genuinely align; use a guided single-option view or a shortlist when columns would become unreadable. Never let presentation erase a disqualifying constraint, the meaning of a feature, or the full cost.

### Two superficially conflicting research findings

- **Specification-heavy physical products:** Baymard observed that an **optional** “Only show differences” control reduces scanning effort when many attributes are genuinely identical. Group attributes into meaningful categories and preserve item identity during long vertical scrolling. Difference highlighting is a weaker fallback, not an equivalent substitute.
- **SaaS and subscription plans:** Baymard also observed that users often **miss truncated feature lists** and infer an omitted capability is unavailable. Therefore a collapsed teaser is not a safe substitute for the full plan matrix. Provide an immediately discoverable full feature inventory; an optional differences filter may operate *on that complete inventory*, but must be reversible and must not imply hidden items do not exist.
- **Why both can be true:** filtering out confirmed **identical** rows is not the same as concealing **unshown** features. The comparison domain, completeness of the underlying data and whether users know what to look for determine which technique helps. Neither source proves a universal winning layout.

### Data and decision contract

1. **Normalize before comparing:** align units, date ranges, currencies, storage/seat limits, plan tiers and inclusion conditions. “Unlimited”, “up to”, “available as add-on”, “not available”, and “unknown/not disclosed” are distinct values. Do not treat missing data as “No”, or approximate equivalence as identical. For price, expose billing interval, renewal/introductory conditions, taxes/fees where known, and the basis of the total. Attribute explanations should be available in plain language, not brand jargon.
2. **Preserve orientation:** show compared item names and decisive constraints with their columns; keep long matrices grouped by task-relevant categories. If using sticky headers, verify they remain visible without obscuring content at 200–400% zoom or in nested scroll containers. Sticky UI is an enhancement, not a substitute for semantic header associations.
3. **Offer reversible focus:** an explicitly labeled “Show differences only” control may hide rows *only when every compared value is reliably equal under a documented comparison rule*. Keep “Show all features” obvious and preserve the chosen items, scroll position when practical, and filter state. Announce a concise changed-row count; if zero differences remain, say so and provide the restore action. Do not auto-enable differences-only as a universal default.
4. **Make exclusions and explanations explicit:** render text for yes/no/partial/unknown, not color or an unlabeled checkmark alone. Define ambiguous capabilities beside their rows with an accessible, keyboard/touch-operable disclosure; if using hover/focus popups, satisfy WCAG 1.4.13 (dismissible where required, hoverable, persistent). For important constraints, do not require opening a tooltip to discover them.
5. **Responsive comparison:** first try a bounded horizontally scrollable semantic table with a visible horizontal-scroll cue and legible row/column identity. Where users primarily compare *one option at a time*, a selector with repeated labeled attributes can be clearer, but it increases memory demands for cross-option judgments. Never convert a comparison matrix into cards that silently remove attributes. WCAG 1.4.10 permits two-dimensional scrolling for data tables, **not** for unrelated page content or individual text cells.
6. **Accessibility:** use a real `<table>`, descriptive `<caption>`, column/row `<th scope>`, and explicit `headers` associations when headers are irregular. Ordinary table reading does not justify `role="grid"`. Keep the comparison toolbar, remove-item actions, and restore-all action operable with keyboard and screen readers; check reading order and focus after adding/removing options.

### Falsification and implementation tests

Seed near-identical options, an unknown value, a feature present in all plans, an add-on masquerading as included, mismatched units, introductory-versus-renewal pricing, and a hidden disqualifying requirement. Compare **full matrix**, **optional differences-only**, and **single-option switching** using matched novice/expert tasks. Measure correct choice and missed constraints first, then time, feature comprehension, recovery, and subjective preference. Test narrow viewports, 400% zoom, horizontal scroll, keyboard/AT, tooltip dismissal, sticky-header occlusion, changing the compared set and no-difference results. Do not count faster scanning as better decisions without checking accuracy.

**Evidence boundary (reviewed 2026-10-23):** Baymard's product and SaaS usability observations support the context-specific distinctions, not a controlled universal ranking. Adobe Research's 2023 mobile table experiments (590 participants; 14,000+ trials across 28 tables) found faster tasks with smaller cell padding and frozen headers; row borders/zebra striping improved preference without faster tasks. Those experiments concern *table reading*, not subscription choice or conversion. W3C defines markup and reflow/hover constraints, not business outcomes.

## Data tables: preserve table navigation before adding grid behavior — 2026-10-13

**Decision:** start with a semantic HTML `<table>` for information organized in rows and columns, **even when columns can be sorted or rows contain links/buttons**. Use an interactive ARIA `grid` only when **managed arrow-key navigation** materially improves the task: spreadsheet-like editing/selection **or** link-heavy rows where ordinary Tab navigation would be excessively long. A table with action buttons is not automatically a grid; a grid introduces its own focus and assistive-technology obligations.

### Three interaction contracts

1. **Reading/comparing:** native `<table>`, a useful `<caption>`, `<th scope="col|row">` and, for irregular/multi-level headers, explicit `id`/`headers` associations. Prefer simplifying an overly complex table before adding ARIA. Native table navigation and ordinary tab order remain available.
2. **Sorting/selection/actions:** keep table semantics; make sortable header labels actual `<button>` elements and set `aria-sort="ascending|descending"` on the **currently sorted header**. `aria-sort` announces state; it does **not** sort records. Provide visible sort direction, a stable tie-breaker, and an understandable result count. Checkbox row selection and action menus can remain normal controls. Avoid turning the entire table into `role="grid"` solely for these features.
3. **Dense keyboard navigation or spreadsheet-like manipulation:** a grid is a composite widget with **one entry in the page Tab sequence** and author-managed arrow-key focus among cells. This may be worthwhile even for many linked records, but **every meaningful cell must be focusable or label a focusable target**: screen readers often switch to application mode and can miss otherwise inaccessible cell text. For editors/comboboxes, provide a deliberate navigation-versus-interaction mode (`Enter`/`F2` to enter, `Escape`/`F2` to return as appropriate); arrows cannot simultaneously navigate cells and move a caret. Test keyboard, touch and screen readers rather than assuming an ARIA role implements the behavior.

### Operational failure boundaries

- **Sorting:** changing a sort key must update both the actual row order and the announced sort state. WAI-ARIA can describe only limited multi-column precedence; expose multi-sort priority in visible text and an accessible description instead of assigning `aria-sort` to every header. Do not rely on hover-only sort affordances.
- **Whole-result-set integrity (server-backed tables, verified 2026-10-24):** filtering, sorting and pagination must operate over the *same logical dataset* before slicing it into pages. TanStack Table v8 explicitly warns that client-side sorting with server-side pagination sorts only the loaded page. Its `manualSorting`, `manualFiltering` and `manualPagination` options **bypass** those client row transforms; the caller must implement all three on the backend, pass the correct totals, and keep the displayed sort/filter state synchronized with the response. Never label a page-local transform as sorting/filtering “all results.” A query key should include the effective filter, sort, page/cursor and tenant/scope; reject stale responses that arrive after a newer query (agent implementation synthesis, not a TanStack guarantee).
- **Stable pages are a data contract, not a paginator decoration:** PostgreSQL 18 warns that `LIMIT`/`OFFSET` without a uniquely determining `ORDER BY` can return unpredictable subsets. Add a deterministic unique tie-breaker when user sort values tie; even then, concurrent inserts/deletes can shift *offset* page boundaries, so choose cursor-based traversal or a consistent snapshot when the task requires no duplicates/omissions across pages. TanStack v8 disables automatic page-index reset under `manualPagination`; explicitly reset/clamp an invalid page when filter/sort/page size or result count changes. Its unknown `pageCount: -1` makes `getCanNextPage()` always true: drive “Next” from an authoritative `hasNext`/cursor signal instead of assuming that API knows the end.
- **Selection:** keep selected row IDs distinct from visible page indices and from all matching results. A filter or page change must not silently change the action scope; see the existing bulk-selection contract. Stable row identity is essential during reorder, refresh and pagination.
- **Large data:** paginate when users need location, returnability and a bounded working set. Virtualization renders only a window and changes the accessibility contract: represent known full counts (or unknown `-1`) and absolute row/column positions correctly where required; verify focus does not disappear when an edited/selected row unmounts. **Vendor-documented counterexample (AG Grid, reviewed 2026-10-19):** virtualized rows/columns and sticky group rows can create DOM/visual-order mismatches for screen readers. Its accessibility guidance recommends `ensureDomOrder`, disabling sticky group rows and, when practical, pagination with virtualization disabled; it also documents grouped-header announcements and server-side unknown-row-count limitations. These mitigations trade memory/rendering performance for navigability and require AT testing on the exact configuration. Do not infer that a library's 100k-row demo proves accessibility or performance.
- **Responsive:** preserve the ability to compare across columns. Horizontal scrolling with clear affordances and stable row identifiers may be better than turning every row into an unrelated card. A card/list adaptation is reasonable when each item is consumed independently, but it must retain labels, actions, order, and relationships; test 200–400% zoom and keyboard access. Reduce/split columns when possible instead of shrinking all text.
- **State changes:** sorting, filtering, pagination and inline edits must preserve focus or move it to a predictable successor, keep URL/return context when appropriate, and announce important result changes without flooding live regions. Validate empty, loading, error and stale-data states separately.

### Virtualized collections: ARIA positions do not preserve focus — 2026-10-26

**Decision:** Virtualization is a rendering optimization, **not** a keyboard-navigation or accessibility implementation. Choose the widget contract first. In a partially rendered **table/grid**, put `aria-rowcount` on the table/grid and `aria-rowindex` on **every rendered row including headers**; positions are **1-based within the current logical filtered/sorted table**, not DOM-window offsets or stable database IDs. The total **includes header rows**; use `-1` only when the total is unknown. For noncontiguous virtualized columns, put `aria-colindex` on **each cell** rather than a row-wide start index. In a partially rendered **listbox/list**, use role-appropriate `aria-setsize` and `aria-posinset` on the options/items; do not mechanically interchange these with table indices. W3C APG warns that missing/inconsistent row or column indices can break assistive-technology table navigation. Correct metadata still **does not make unmounted content available**.

**Focus continuity is a separate invariant.** When the focused row unmounts, DOM focus can fall to `body`. Either retain the active row within a bounded virtual window or transfer focus deliberately to a meaningful mounted successor **before** removal; preserve stable item identity, selection and draft state. With container-focused `aria-activedescendant`, WAI-ARIA 1.3 requires a real accessibility descendant (or qualifying controlled popup descendant): do not leave a stale ID pointing to an unmounted option. Mount/scroll the active option before referencing it, or select a visible successor. Do not jump the user during passive updates.

| Case | Release gate |
|---|---|
| Partial table, two headers, unknown total | Include headers in total/absolute indices; every rendered row indexed in increasing order; unknown `aria-rowcount=-1` only when genuinely unknown. |
| Virtualized listbox or combobox popup | Each item has role-appropriate set position; `aria-activedescendant` resolves to an accessible mounted option throughout keyboard/scroll/filter changes. |
| Focused editor removed by scroll/filter/delete | Focus and unsaved input remain usable, or move to a predictable mounted successor; no silent focus-to-body. |
| Pinned or skipped columns | Absolute cell indices, visual/DOM order, header associations and keyboard reachability survive virtualization. |
| Huge result set | Measure AT access, DOM/memory and input latency; consider bounded pagination as a control rather than assuming a 100k-row demo is usable. |

**Narrow browser probe (2026-10-26):** Three identical Chromium 144.0.7559.96/Playwright Python runs: removing the `<tr>` containing a focused button changed `document.activeElement` to `BODY`; focusing a mounted successor *before* removal retained focus on `BUTTON#successor`. Removing an option referenced by a focused listbox's `aria-activedescendant` left the stale DOM attribute, while Chromium's CDP accessibility tree no longer exposed its resolved `activedescendant` relation. This is an isolated DOM/AX counterexample, **not** a real virtualizer, cross-browser/AT test or measured user outcome. See `research/SOURCES.md` and `research/OPEN_QUESTIONS.md`.

**Agent acceptance test:** compare a read-only table, a sortable/action table, a link-dense table versus grid, and an editable grid using keyboard and screen reader. Measure Tab stops *and* missed cell content; test sort order versus `aria-sort`, selection across pages/filters, long/grouped headers, sticky/pinned columns, horizontal scroll, 400% zoom, row removal during edit, virtualization boundaries, unknown server-side counts, RTL and touch. **Server-pipeline falsification:** seed two pages with interleaved sort values (page A: 10, 1; page B: 9, 2), tied values with distinct IDs, a filter matching an off-page record, out-of-order responses, a page-index change to an empty page, and a concurrent insert between page fetches. Assert backend-wide sorted/filtered IDs and stable action scope, not just a correctly oriented header arrow. A clean automated accessibility scan is not proof that composite-grid navigation works.

**Evidence boundary:** W3C/APG establishes semantic and keyboard contracts (including link-heavy grids as a possible Tab-stop optimization); GOV.UK and Carbon show deployed design-system choices; React Aria documents a grid implementation with a separate Tab navigation mode for interactive cells; TanStack describes pagination/virtualization trade-offs. AG Grid documents concrete limitations of its own implementation, not universal failure prevalence. None is a controlled comparison proving a grid, pagination or responsive cards universally superior.

## Navigation and wayfinding

Design navigation from the **task topology**, not from a preferred component. First determine whether the experience is primarily a linear transaction, repeated multi-task workspace, hierarchical information space, or a mixture with explicit boundaries.

### Do not add global navigation by default
A clear end-to-end transaction often benefits from fewer escape routes and stronger progression cues. Persistent service/product navigation is more justified when users return repeatedly, switch among multiple independent tasks, or need stable access to top-level areas. Navigation is not a sitemap: expose the few durable destinations that describe the product's useful top-level structure rather than every reachable screen.

This distinction is visible in deployed GOV.UK guidance: repeated multi-task services may use service navigation, while clear end-to-end journeys are directed toward task/progress structures instead. Treat that as strong production guidance for the mechanism, not proof that government information architecture transfers unchanged to every product.

### Separate hierarchy from history and progress
Do not make breadcrumbs, Back, and steppers interchangeable:
- **Breadcrumbs** represent location in a meaningful hierarchy and can provide jumps to ancestors. They are weak when the structure is flat and should not represent transaction progress.
- **Back** represents return to the prior meaningful state. In a transaction, preserve the previous page's state rather than treating Back as a parent-hierarchy link.
- **Progress/task structures** represent position or completion within a process, not information hierarchy.

Avoid showing breadcrumb + Back merely because both are available; redundant navigation adds noise without necessarily adding orientation. GOV.UK explicitly advises choosing between them for its service patterns.

### Preserve stable landmarks, labels, and relative order
Repeated navigation should remain predictable across views. Keep durable destinations in stable relative positions and use consistent labels for the same destination/function. A responsive layout may change presentation (for example, expanded sidebar to disclosure) without changing the conceptual navigation model or silently renaming/reordering core destinations.

WCAG 2.x requires repeated navigation mechanisms to occur in the same relative order unless the user initiates a change. Current WCAG 3 drafts continue to develop consistent structural order, navigation order, and labels; treat draft WCAG 3 material as directional, not yet normative.

### Expose current location without relying on styling alone
Users should be able to identify the current page/section from page title/heading plus navigation state. Mark the current destination semantically where appropriate (`aria-current="page"` for the current page link); distinguish “current page” from “inside this section” when the design system supports both concepts.

### Preserve returnability
Navigation quality includes what happens after leaving a list, workspace, or transaction step. Preserve meaningful query/filter state, selection, scroll/location, and unsaved work according to product semantics. Browser back/forward and deep links should not become second-class paths. Do not create a custom Back control that contradicts browser history or reconstructs a different state.

### Responsive navigation is an information-architecture decision
Do not solve narrow screens by hiding arbitrary destinations. Preserve the priority and naming of core destinations; change presentation when necessary. If secondary destinations move behind a menu, keep the current location understandable and keyboard/focus behavior coherent. Avoid duplicating the same active navigation tree in two simultaneously focusable DOM regions just to support breakpoints.

### Navigation contract for agents
Before implementing navigation, answer:
1. What are the stable user-recognizable objects/areas?
2. Is the dominant journey hierarchical, linear, multi-task, or mixed?
3. Which destinations must remain globally reachable, and which belong only in context?
4. What does Back mean here: history, parent, cancel, or previous process step?
5. What state must survive leaving and returning?
6. How is current location communicated visually and semantically?
7. Does responsive transformation preserve the same conceptual model?
8. Can keyboard, assistive-technology, deep-link, refresh, and browser-history paths reach equivalent states?

### Failure modes
- mirroring backend modules or org charts as navigation without validating user concepts;
- using breadcrumbs as a history trail or progress indicator;
- persistent global navigation inside a focused transaction where it mainly creates exits;
- mega-navigation that exposes the sitemap instead of prioritizing destinations;
- moving/renaming repeated destinations between pages without a user-controlled reason;
- mobile navigation that hides critical state or changes the information architecture accidentally;
- custom history behavior that loses form/filter state or fights browser Back;
- icon-only primary navigation whose meaning depends on memorization.

### Implementation checks
Test direct entry on deep pages, refresh, browser back/forward, return from detail, expired/auth-changed sessions, unsaved state, keyboard traversal, skip links/landmarks, screen-reader current-location announcement, zoom/reflow, long/localized labels, narrow/wide transitions, permission-dependent destinations, and URLs copied into a new session.

## Navigation evidence boundary
WCAG 2.x provides normative accessibility requirements for consistent repeated navigation; WCAG 3 material reviewed in October 2026 is still draft and should not be treated as a final requirement. GOV.UK provides current deployed guidance that clearly separates hierarchical breadcrumbs, historical/process Back, and repeated multi-task service navigation. These sources strongly support semantic separation and predictability, but they do not prove one navigation shell, sidebar pattern, or information architecture is universally superior.

## Command palettes: accelerator, not navigation replacement — 2026-10-14

**Decision:** add a searchable action launcher when a repeat-use, multi-task workspace has enough commands or destinations that keyboard-first retrieval materially reduces navigation cost. Do **not** replace visible primary navigation, search, or contextual controls with a hidden `Cmd/Ctrl+K` interface. A command palette is an **expert accelerator and discovery aid**, not proof of better usability.

### Separate intents and scope

- **Go to** navigates to an existing resource; **Find** searches content or records; **Do** executes a command. Keep these distinguishable in labels, result groups and empty states. Linear ships separate workspace search (`/`), view search (`Cmd/Ctrl+F`) and a contextual command menu; GitHub's command palette scopes suggestions to the current location and offers explicit resource-type prefixes. These are examples of deployed patterns, **not** measured evidence that one unified palette is always preferable.
- Make scope visible (workspace, project, current selection) and avoid stale-context actions. When the selection, permissions, or active workspace changes, re-evaluate available actions before execution. A result labeled “Delete” is not safe if it silently targets an earlier selection.
- Show human-readable verbs and object names, with destructive/irreversible actions clearly distinguished. Palette search and Enter should **not** bypass the same confirmation, authorization, undo and server validation required by the ordinary UI. A disabled result needs a useful reason; hide unauthorized data rather than merely disabling its command.
- Keep a visible launch button or menu entry, show the shortcut as a hint, and retain ordinary discoverable routes to essential actions. Provide meaningful empty results, recent/relevant suggestions where justified, and a way to recover from a mistaken command.

### Keyboard and accessibility contract

- An overlay palette that blocks the underlying page needs a correctly named **modal dialog** with initial focus in its search input, contained Tab sequence, Escape close, and logical focus return. A non-modal palette must not falsely claim modality. Search input plus suggestions can use the **combobox/listbox** pattern when its focus and selection semantics fit; a list of executable actions is **not automatically** a list of values to commit to an input. Choose semantics from actual behavior, not a library's component name.
- Preserve native text-editing shortcuts while the query input is focused. Test arrow-key active option, Enter activation, Escape, IME composition, screen-reader announcements of result count/selection, focus return, and no-results state. Prevent Enter from accidentally running a stale result during asynchronous search.
- **WCAG 2.2 SC 2.1.4 (Level A):** global printable-character shortcuts, including multi-character sequences, must be disableable/remappable to include a non-printable key **or** active only while the relevant component has focus. Merely suppressing them inside text inputs does not satisfy the global-shortcut rule. `aria-keyshortcuts` documents an implemented shortcut; it does not implement it or make it discoverable.
- Test `Cmd/Ctrl+K` against browser/OS/assistive-technology shortcuts and text editing; do not globally swallow collisions. Let users access all important functions without memorizing key combinations.

### Agent implementation and falsification

Start with the app's **authoritative action registry** (stable ID, verb, label, scope, availability predicate, permission check, navigation/action handler, risk and recovery), then render visible controls and palette entries from compatible contracts. Re-check context/permissions at execution; do not trust a client-side list as an authorization boundary. Compare a visible-navigation-only baseline with an added palette on novice/expert, keyboard/touch/voice-input tasks; measure command discovery, completion/error rate, mistaken destructive actions, shortcut conflicts, time and focus recovery. A successful keyboard demo or shipped example does not establish net UX benefit.

**Evidence:** shipped behavior: [Linear search](https://linear.app/docs/search), [Linear selected-item actions](https://linear.app/docs/select-issues), [GitHub command palette](https://docs.github.com/en/enterprise-cloud@latest/get-started/accessibility/github-command-palette), [VS Code shortcuts](https://code.visualstudio.com/docs/configure/keybindings). Normative/technical: [WCAG character shortcuts](https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts), [W3C combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), [W3C modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [MDN aria-keyshortcuts](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-keyshortcuts). No comparative user-outcome evidence was established in this cycle.

## Reordering and drag-and-drop: design the non-drag operation first

**Decision rule (reviewed 2026-10-09):** Model the operation as *move item X to position/group Y* before choosing drag gestures. A draggable UI is an optional input method for that operation, not its sole definition. For a small ordered list, visible **Move up / Move down** buttons may be sufficient without any drag library. For cross-column boards or large lists, offer a click/tap-operable **Move to…** menu or destination chooser as well as dragging. Preserve the same permissions, ordering rules, and outcome across methods.

### Two independent accessibility obligations

- **Keyboard operation** (WCAG 2.1.1) requires a usable keyboard path; a keyboard sensor can help, but keyboard-only drag is not enough.
- **Single-pointer operation without dragging** (WCAG **2.5.7, Level AA**) separately requires click/tap alternatives for author-controlled drag operations unless the defined exception applies. A drag handle operated by arrow keys alone does **not** satisfy this criterion for someone using touch without a keyboard. A menu or buttons that can be activated by a single pointer can serve both obligations. This distinction is explicit in [W3C's understanding of 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements) and [technique G219](https://www.w3.org/WAI/WCAG22/Techniques/general/G219).

### Interaction contract

1. **Discoverability:** make movable items identifiable without hover alone. If an item contains links, buttons, text selection, or editable content, use a dedicated drag handle rather than hijacking the entire item's pointer behavior. Expose the equivalent action menu on the item.
2. **Before moving:** distinguish manual rank from current *display order*. If results are sorted by date/name or filtered, either disable manual reordering with an explanation and a route back to rank order, or define precisely what the change means. Do not silently reorder hidden rows or mutate the wrong canonical sequence. [Jira's April 2026 list rollout](https://confluence.atlassian.com/cloud/blog/2026/04/atlassian-cloud-changes-mar-30-to-apr-6-2026) demonstrates the disable-with-explanation choice (shipped behavior, not measured UX superiority).
3. **During moving:** show the proposed destination (before/after/on another item or into a group), distinguish *move* from *copy*, and support cancellation without committing changes. Do not use motion or color as the only indicator.
4. **After moving:** announce a concrete outcome such as “Task A moved from To do to Doing” or “Item B moved to position 2 of 8”; retain or restore focus to a meaningful control for the moved item, including when the item remounts in another parent. Preserve selection and scroll context where sensible. For consequential/remote moves, provide error recovery and a durable undo path.
5. **Boundaries:** disable impossible moves explicitly (first item up, locked group, invalid drop target). Make failed drops and server rejections visible and reversible; avoid optimistic visual success that silently rolls back.

### Choose the implementation by semantics and ownership

- **Buttons/menus first:** the least complex robust option for basic reorder/move operations, and an essential complement to drag in many richer interfaces.
- **Atlassian Pragmatic drag and drop:** framework-agnostic, native-browser drag core with optional visuals; **the core does not implement accessible alternatives for you**. Atlassian's [accessibility guidance](https://atlassian.design/components/pragmatic-drag-and-drop/accessibility-guidelines/) favors explicit move menus, live announcements and focus continuation over making arrow-key dragging the only alternative.
- **React Spectrum:** its [drag-and-drop collections](https://react-spectrum.adobe.com/dnd) include keyboard and screen-reader drag mode, target navigation, announcements and mobile screen-reader interaction. This is a stronger integrated interaction model for supported React collection components, but requires checking the actual version, app integration and AT behavior; it is not a reason to replace a simple move menu.
- **Raw HTML `draggable`:** [MDN](https://developer.mozilla.org/en-US/docs/Web/API/HTML_Drag_and_Drop_API) documents drag events and a text-selection tradeoff; setting `draggable=true` does not supply keyboard semantics, single-pointer alternatives, announcements or focus restoration.
- **WAI-ARIA APG rearrangeable listbox:** [illustrative example](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/examples/listbox-rearrangeable/) combines listbox actions, move buttons and live status. Do not copy its `listbox` role onto an ordinary list of interactive cards: listbox is a selection widget with its own keyboard contract. APG warns its examples need browser/AT testing and are not production-ready components.

**Design disagreement worth preserving:** Atlassian discourages directional-key movement as a general accessibility strategy because it can be awkward for screen readers and complex boards; React Spectrum supports keyboard drag/drop for richer collection navigation; W3C APG shows move-up/down controls for a rearrangeable listbox. These are context-specific approaches, not mutually exclusive universal standards. The common invariant is **equivalent, discoverable operations and recoverable feedback across input modes**.

### Validation / evidence boundary

Test click/tap-only (no dragging or physical keyboard), keyboard-only, screen reader on desktop and touch, item remount/focus, long lists/scroll, zoom, RTL, nested interactive controls, multiple selection, invalid targets, sort/filter changes, async save failure, and drag cancellation. Add file-input alternatives for file upload drop zones. Standards establish required input equivalence; library documentation describes mechanisms; the Jira rollout shows a production constraint. None establishes that dragging improves completion time or satisfaction compared with menus. Measure that separately before adding a gesture-heavy interaction.


## File uploads: separate selection, transfer and acceptance

**Decision rule (2026-10-10):** A selected file is not an uploaded file; a completed network transfer is not necessarily an accepted file. Model per-file states explicitly: selected → validating → transferring → server processing → accepted, with distinct rejection, failure, cancellation and retry paths. Never announce “Uploaded” solely because a progress indicator reaches 100%.

### Choose the interaction
- Start with a labelled native `<input type="file">`, descriptive format/size/count hints, and a working non-JavaScript path. Drag-and-drop is optional progressive enhancement; retain the picker for touch, keyboard and assistive technology. GOV.UK introduced an enhanced accessible picker in March 2025, while USWDS documents an outstanding focus-indicator issue in its own enhancement.
- For distinct required documents, prefer separately labelled controls; for interchangeable batches, allow multi-selection or “Add another”. USWDS notes that multi-selection can be unfamiliar and its file-input component does not upload asynchronously; avoid falsely marking selected files as uploaded.
- Before upload, identify specific problems: wrong type, size, empty file, count limit or template mismatch. Preserve unaffected files and form data. Let users reuse previously accepted files in the same journey when privacy permits.

### Transfer, processing and recovery
- Show per-file status and aggregate batch count. Only show determinate percentages when measured; `XMLHttpRequest.upload` provides progress events, but `lengthComputable=false` means a trustworthy percentage is unavailable. Avoid announcing every percentage tick through a live region.
- Distinguish “Transferring” from “Processing / checking” and “Ready”. HMRC's deployed upload pattern announces success after the file has been received **and scanned**, not merely after bytes have arrived.
- Provide a clear Cancel/Retry/Remove or Replace operation as appropriate. Client cancellation may not immediately delete partial server data; design status accordingly. On partial batch failure, retain accepted files and retry only affected items. Test same-file re-selection, refresh/navigation, timeouts and slow connections.
- Resumable upload is a **protocol choice**, not a visual feature. The tus 1.0 specification uses `HEAD` to recover the server-confirmed offset and `PATCH` to continue; mismatched offsets return `409`. Handle expiration, authorization and cleanup before promising recovery after interruption.

### Validation boundary
The HTML `accept` attribute only guides the file picker; it does not replace server-side checks. Apply file size/type/content validation and safe storage on the server. A thumbnail or client-side parse is not evidence of acceptance. Keep original file names and private previews from being exposed unintentionally.

**Agent checks:** native picker, drop, keyboard/touch, screen reader, mobile file providers, duplicate names, invalid/empty/oversized files, partial batch success, 100%-transfer-then-server-rejection, cancellation, retry, stale progress, focus and status announcements, and no-JS fallback. Measure whether users complete the task; official design-system patterns and platform APIs establish implementation mechanics, not universal UX superiority.
